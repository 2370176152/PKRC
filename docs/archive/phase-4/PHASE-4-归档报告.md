## 七、经验沉淀（方法论级）

| # | 沉淀 | 来源 |
|---|---|---|
| 1 | **「门被自己锁住」是阶段治理最隐蔽的故障** | O-5 的"先修完才判"在第三阶段是正确的（防挂账），但在第四阶段变成了死锁。<br>**判据的严格性要与"能否达成"一起验证**，否则越严格越僵 |
| 2 | **能力建设完成 ≠ 阶段完成** | 本阶段 10 项能力建设全绿、覆盖率 +7.16 pt，但出口判据 0/7 —— 因为判据全部指向"验证结果"而非"验证能力" |
| 3 | **切换产物会污染自己的度量工具** | A5-01 切换后 `verify-signature.cjs` 的 baseline 指向了候选本身 ⇒ 覆盖率虚高 ~100% ⇒ 足以误判 M3。<br>**凡"基准 = 候选"的工具，切换类操作后必须复查** |
| 4 | **走查环境的价值在建成的第一天兑现** | F-10 首跑即抓到 P0 启动阻断缺陷 —— 这个缺陷在纯静态验证里看不出来 |
| 5 | **「需 GUI」这类判断必须定期复查** | A4-03 被第三阶段判为"需 GUI"，本阶段用 Node 沙盒 38/38 通过。<br>**判断偏严和白等一个阶段是同一件事** |
| 6 | **换靶比硬啃更划算** | eryou-ui 2 批 0 收益（2 次回滚）vs 五孤岛 7 批 +97。<br>**发现某靶子连续两批零收益，就该换，而不是加码** |
| 7 | **同一仓库的 git 写操作必须串行** | 并行两条 `git commit` 触发 `index.lock`，一条失败 |
| 8 | **「未定性残差」≠「迁移缺陷数」** | 533 残差中 507 是"src 根本没有"，另有 210 是 tree-shake（src 有、无入口）。<br>混为一谈会得出"缺口巨大"的错误结论 |
