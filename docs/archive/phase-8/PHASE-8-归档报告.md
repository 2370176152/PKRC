## 二、技术突破：从"看 DOM"换成"读游戏状态"

### 2.1 死结（实测，不是推测）

| 探测项 | 实测结果 |
|---|---|
| `document.body.innerText` | **长度 0** |
| `document.body` 子节点 | 只有 `#app` + `#touchControls` |
| `Phaser.GAMES` | 不可用 |
| `window.game` | 不存在（`main.ts` 里是局部变量） |

**全部 UI 渲染在单个 canvas 里 ⇒ DOM 断言对游戏内画面完全失效。**

> **这就是第 5~7 阶段所有 route 只能给"画面变了"这种弱证明的根因。**
> 不是 route 写得差，是**根本没有可断言的锚点**。

### 2.2 解法

**① 一行只读观测句柄**（`src/main.ts`）

```ts
Object.defineProperty(window, "__PKRC_GAME__", {
  value: game, writable: false, configurable: false, enumerable: false,
});
```

> **纯观测**：只把已存在的 `game` 实例挂到只读全局。不创建、不修改、不驱动任何逻辑。
> 去掉这一行不影响游戏任何行为。

**② `catalog.mjs` 用 `waitFor` 读真实状态**

```js
REACH_IN_RUN  →  waveIndex > 0 && getPlayerParty().length > 0
REACH_READY   →  phaseManager 已有可用 Phase
```

**结果**：`reachProof` `none` → **`dom`**，判定 `unproven` → **`pass`**。

### 2.3 四个致命细节

| # | 问题 | 后果 | 修法 |
|---|---|---|---|
| 1 | **`taps()` 连按只间隔 60ms** | 游戏吃不到按键 —— **所有 route 一直失败的真凶** | `tapsSlow(key, n, 800)` + 显式 `wait` 步骤 |
| 2 | ready 通过时 `LoginPhase` 过场仍在跑（实测 t=14s） | 前几次按键被吞 | 先 `wait(5000)` |
| 3 | A 产物无句柄 | A 全 `unreached` ⇒ A/B 对比失效 + "探针不可用"被误报成"画面到不了" | 探针缺句柄时 `return true`（放行） |
| 4 | `verified` 点加探针 | 强档反被降级成 `unreached` | 49/51 加，2 点保留原强证明 |

> **细节 #1 值得单独说**：它是"工具的使用方式错了"，不是"被测对象有问题"。
> 前三阶段的 route 一直失败，**不是因为画面到不了，而是按键根本没送达**。
> **这类 bug 最贵 —— 它会让你去错的地方找原因。**

## 五、经验沉淀

| # | 沉淀 | 来源 |
|---|---|---|
| 1 | **"DOM 断言失效"≠"无法证明到达"** | 换锚点：从 DOM 换到游戏内部状态（`waveIndex` / party / phaseManager）。**证明到达不一定要看 DOM** |
| 2 | **最难查的 bug 在"工具的使用方式"里** | `taps()` 间隔 60ms ⇒ 游戏吃不到按键。**route 全错不是画面到不了，是按键没送达** |
| 3 | **给被测产物加观测点必须"只读"** | `Object.defineProperty` + `writable:false` + `configurable:false`。**"为了测试改产品"会污染被测对象** |
| 4 | **探针缺失要"放行"而不是"判失败"** | A 产物没句柄时 `return true`。**不要把工具的限制记成产品的缺陷** |
| 5 | **重复请求先核对状态** | 同样的话第二次说，不代表要第二次做 |
| 6 | **缺口性质的变化比缺口大小更重要** | 「36~39 点没有证明方法」→「5 点进不了战斗」：**数字变少了，但真正的变化是"结构性"变成"单点"** |
