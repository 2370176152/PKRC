## 二、🔴 本阶段最重要的发现

### 2.1 自构建产物从来没真正启动过

**B 一直停在登录页。**

| 项 | 内容 |
|---|---|
| **症状** | 无报错。走查能打开页面、能截图、`stdDev` 有变化 —— 一切"看起来正常" |
| **根因** | `vite build` 默认 `production` mode ⇒ 读 `.env.production`（`VITE_BYPASS_LOGIN=0`）⇒ 编译期 `bypassLogin=false` ⇒ **必须登录** |
| **对照** | modder 原产物 A 是 `bypassLogin=true` |
| **修法** | 改用 `vite build --mode app` |
| **实证** | 修后产物内 `Log in or create an account` 由 **1 → 0**；截图显示 B 首次进入游戏欢迎页 |

**⇒ 此前所有走查（第五/六/七阶段）测的都是「登录页上点几下」。**

> **这解释了为什么"走查"一直跑不出有意义的结果** ——
> 不是工具不行、不是场景不够、不是 route 不明，**是被测对象根本没进游戏**。

### 2.2 一个反直觉的交叉验证

| 观察 | 含义 |
|---|---|
| **两次跑（B 停在登录页 / B 已进游戏）裁定分布完全相同** | ⇒ **不变量在 route 层，不在启动层** |
| A：pass 2 / unproven 39 / unreachable 9 / blocked 0 | `unproven` 的成因是 route 缺到达证据，**与产物是否启动无关** |

> 这个交叉验证的价值：它证明「修好启动」**不会**自动让走查变绿 ——
> 两个问题是独立的，必须分别解决。**否则修完启动会误以为走查该好了。**

### 2.3 5 个 P0 全部只有真跑才现形

| # | 报错 | 根因 | 触发时机 |
|---|---|---|---|
| 1 | `safeT is not defined` | 悬空 declare，`TALENT_POOL` 在**模块求值期**调用 | import 时 |
| 2 | `FixedBattleConfig is not a constructor` | **循环导入**（6 跳链） | import 时 |
| 3 | `createSpeciesPartyWeightModifiers is not defined` | 悬空 declare，走**启动路径** | `initializeTalentSystem` |
| **4** | **停在登录页（无报错）** | **构建 mode 错** | 编译期 |
| 5 | `ii / Ht / $l / Yi is not defined` | 15 处 `extends <declare 短名>` | import 时 |

**tsc EXIT=0 · vite build EXIT=0 · 签名 11/11 · 走查能截图** —— **五道静态关卡全部放行。**

> 🔴 **这是本项目最重要的一条教训**：
> **静态检查只能证明"名字存在"，不能证明"运行时不会崩"。**
> `clear-declares.cjs` 能告诉你 declare 有没有依赖，但回答不了它会不会在启动路径上被调用。

## 五、为什么 I-7 选择"不解除标注"

I-7 的验收是「解除 `dist/` 的「未验证」标注」。本阶段**主动选择不解除**，理由三条：

1. M4 未达成（战斗全流程未验）
2. `addPt` 活体未证
3. L1-2 到达证明缺失（`unproven` 76%）

> **如实保留标注，比"解除后被打脸"更有价值。**
> 标注的存在意义就是"在没验完时告诉使用者" —— 此时解除，标注就失去了全部意义。
