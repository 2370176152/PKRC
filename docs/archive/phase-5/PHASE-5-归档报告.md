#### B-15 纠正了一个会让人白干的事实错误

`A4-03` §5 原文：「`.prsv` 层 = **BlowFish**」。**这是误读压缩符号。**

锚点源码逐字（`src/system/game-data.ts:1359`）：
```ts
const encryptedData = AES.encrypt(data, saveKey);   // ← 只有 AES
link.download = `${dataKey}.prsv`;
```
`grep -rln "BlowFish|blowfish" src/` → **零命中**。

⇒ A4-03 的「补验路径②：提取产物 BlowFish 函数体」**在追一个不存在的东西**，已作废。

> **教训**：压缩符号会骗人。`qo`/`FI` 看起来像 BlowFish 的实现，但那只是 minified 后的短名。
> **凡从产物反推算法，必须回到源码或行为验证，不能靠符号形态猜。**

## 五、🔴 已定位的模式缺陷（本阶段最重要的反思）

**连续三个阶段的形态完全一致**：

| 阶段 | 建成了什么 | 判据/里程碑达成 |
|---|---|---|
| 第三阶段 | 接入锚点 22/22 + 环境修复 + 8 项交付 | M3 条件达成（后判不合格） |
| 第四阶段 | 10 项能力（F-10 走查环境 · B-7/9/10/11 · A4-03） | **0 / 7** |
| 第五阶段 | 走查全链路（51 点 · 五态裁定 · 闸门 · 取证 · 回归 · 演练） | **1 / 7** |

**共同点：每个阶段都在"建工具"，而"用工具"从未开始。**

**根因分析**（不是执行力问题）：

1. **规划缺陷** —— 每个阶段都把「建成使能件」和「执行验证」放进同一阶段，
   而使能件本身就要吃掉整个阶段。
2. **使能件有天然的"再完善一点"倾向** —— 51 点里有 27 点 route 是 unknown，
   很容易想"再补完再跑"。但**跑一次才知道哪些 unknown 真的到不了**。
3. **验收判据写的是"建成"，不是"跑通"** —— 所以阶段自然地停在"建成"那一刻。

**⇒ 第六阶段的硬约束**（已写入派单）：

> **禁止新建任何工具 / 使能件 / 框架。只允许"执行既有能力 + 修被暴露的缺陷"。**
> 若确需新工具，必须由所有者批准并说明为何现有能力不够。

**并且**：第六阶段的出口判据全部写成"**跑通并产出数据**"，不写"建成"。
