## 二、A-1 的技术核心（这是本轮唯一的新增能力）

### 2.1 先说清原来的死结

实测（`document.body.innerText.length === 0`）：

| 探测项 | 结果 |
|---|---|
| `document.body.innerText` | **长度 0** —— 全部 UI 渲染在单个 canvas |
| `document.body` 子节点 | 只有 `#app` + `#touchControls` |
| `Phaser.GAMES` | 不可用 |
| `window.game` | 不存在（`main.ts` 里是局部变量） |

⇒ **DOM 断言对游戏内画面完全失效**（U-11 当初的判断是对的）。
这也解释了为什么第 5~7 阶段所有 route 只能给「画面变了」这种弱证明 ⇒ 全部 `unproven`。

### 2.2 解法（一行产品代码 + 一套探针）

**① 暴露只读观测句柄**（`src/main.ts`）

```ts
Object.defineProperty(window, "__PKRC_GAME__", {
  value: game, writable: false, configurable: false, enumerable: false,
});
```

⚠️ **这是纯观测**：只把**已存在**的 `game` 实例挂到只读全局，不创建、不修改、不驱动任何逻辑。
去掉这一行不影响游戏任何行为；保留它只是让自动走查有可断言的锚点。

**② `catalog.mjs` 用 `waitFor` 读真实状态**

```js
const PROBE_HEAD = `const g=window.__PKRC_GAME__; ... const s=g.scene.scenes.find(x=>x.gameData); ...`;
const REACH_READY  = () => probe(`const pm=s.phaseManager; ...`, "游戏主流程已起来");
const REACH_IN_RUN = () => probe(`return (s.currentBattle?.waveIndex??0)>0 && (s.getPlayerParty?.()?.length??0)>0;`,
                                 "已进入 run（waveIndex>0 且我方队伍非空）");
```

**③ 结果**：`reachProof` 由 `none` → **`dom`**，判定由 `unproven` → **`pass`**。

### 2.4 🔴 四个致命细节（不修就全盘错，都已修）

| # | 问题 | 后果 | 修法 |
|---|---|---|---|
| 1 | **`taps()` 连按只间隔 60ms**（`runRoute` 里 `delay(s.holdMs?30:60)`） | 游戏**吃不到**按键 —— 这是所有 route 一直失败的真凶 | `tapsSlow(key, n, 800)`，把间隔做成显式 `wait` 步骤 |
| 2 | ready 判定通过时「画面非黑屏」，但 `LoginPhase` 过场还在跑（实测 t=14s 仍在其中） | 前几次按键被吞 | 先 `wait(5000)` 再按 |
| 3 | **A 产物没有句柄**（只加在 B 的 src） | A 全部 `unreached` ⇒ **A/B 对比直接失效**，且会把「探针不可用」误报成「画面到不了」 | 探针在句柄缺失时 `return true`（放行，退回原判定） |
| 4 | `routeReliability === "verified"` 的点被加探针 | 本是 `none-verified` 强档，加「离开 LoginPhase」探针反而**降级成 unreached** | verified 点不加探针（49/51 加，2 点保留原强证明） |
