## 四、🔴 演练抓到的真缺陷：回滚不是「精确恢复」（已修）

### 4.1 现象

第一次演练 B 的断言失败：

```
❌ 目标已恢复为真实产物（文件数回到回滚前） —— 38041→38042 文件 / 756.9 MB
```

**多了 1 个文件。** 逐层追：

| 步 | 动作 | 结果 |
|---|---|---|
| ④ | `target` →rename→ `backups/dist.<ts>` | 备份 = 原产物 |
| ④′ | `writeSumsFile(backupDir)` | **把 `SHA256SUMS` 写进了备份目录**（此时备份 ≡ 原产物 + 1 文件） |
| ⑤ | `staging/dist.new` →rename→ `target` | 坏产物上线，冒烟失败 |
| ⑧ | `target`→`dist.broken-<ts>`；`backup`→rename→`target` | **恢复的是「备份目录」，于是那个 `SHA256SUMS` 一起回到了线上** |

⇒ 回滚 = 「恢复 + 多一个 `SHA256SUMS`」，**不是精确恢复**。
后果虽不致命（该文件运行期不加载，`verify` 只会把它算进 `extras` 告警），但语义是错的：
**回滚一旦不精确，就不能作为「回到事故前」的凭据。**

### 4.2 修法

新增 `removeRestoredManifest(dir, logFn)`：把备份换回目标后，删掉**我们自己写的那份** `SHA256SUMS`。

**只删自己那份** —— 靠首行标记 `# PKRC release backup` 识别，绝不误删产物自带的同名文件。
接入三处恢复路径（**全部都有同样的污染**）：

| 路径 | 位置 |
|---|---|
| F5 切换失败 → 尽力恢复 | `cmdPublish` ⑤ 的 catch |
| F6 冒烟失败 → 自动回滚 | `cmdPublish` ⑧ |
| 手动回滚 | `cmdRollback` |

⚠️ **copy 模式同样污染**（`copyTree(backupDir, target)` 会把清单一起复制过去），所以清理放在 if/else **之后**统一做。

### 4.3 复验

```
演练 B：1.3s · step=smoke · rolledBack=true
✅ 目标已恢复为真实产物（文件数回到回滚前） —— 38041→38041 文件 / 756.8 MB   ← 精确恢复
```

回归测试同步 +1 项（`removeRestoredManifest` 三种情形：自己写的删、别人的不删、不存在返回 false），
`test-release.cjs` **62/62**。

## 五、🔴 另一个必须先解决的阻断（演练 A 第一次跑时暴露）

第一次演练 A 在 **③ 校验** 就停了：

```
step: verify
failures: [ "发现 18 个零字节文件" ]
```

追查：`game/server/dist/images/pokemon/**` 下有 **18 个 0 字节、无扩展名、中文文件名**的文件
（`back/1这里背`、`variant/1这里正`、`back/这里背` …），且它们的源头是**原始发行包 `PKRC.zip`**
⇒ 重新并资产会再带回来。

**这条如果不解决，E-5（A5-01b）的 publish 100% 会被挡住。**

处置：**没有去删 live dist**（那要授权，而且是治标），而是把判定加进**合并期过滤**（B-16 已建的机制）：

| 判定 | 条件 |
|---|---|
| ① 后缀黑名单 | `.zip/.psd/.bak/…` |
| ② **零字节 + 无扩展名**（B-14 新增） | 加载器按 `{id}.png` 精确匹配 ⇒ 无扩展名**永不加载**；0 字节 ⇒ 不含数据 ⇒ 必然是残渣 |

**职责分界**：`findResidue()`（供 `verify` 报告）**不**放宽 —— 零字节文件在 verify 那里必须作为
**失败项**暴露；`pruneResidue()`（供 merge）才清。一句话：**verify 负责把问题顶出来，merge 负责清掉能安全清的。**

修完演练 A 一次通过（`verify` 未跳过）。

**沙箱保护**（踩过坑后加的）：

- 沙箱必须**全新**；非空则**直接拒绝**，不擅自删除 ——
  （实测：上一次中断留下 162 MB / 23k 文件，`fs.rmSync` 在这台机器上要跑 **8 分钟以上**，

- 所有路径操作前 `assertInside()` 校验在沙箱根内。
- 默认演练完清理；清理会**遍历统计释放量**，38k 文件时较慢 —— 需要快就用 `--keep`。

## 八、遗留与边界（如实）

1. **未在真实 `dist` 上执行 `--commit`**（那属 E-5）。本演练用的是**副本流程**：
   同样的产物内容，但目标是沙箱。
2. **`--asset-dir` 用的是线上 dist**（唯一含全 14 类的真实树）。
   等 E-5 落地后，资产源应改为正式资产目录 —— 届时演练输入要同步更新。
3. **备份的 `SHA256SUMS` 只有 1 条**（`--hash=critical` 的默认范围，含 `index.html` / `assets/**` / `pkrc/**`）。
   演练 A 的「旧产物」是我造的 2 文件假 dist，所以只有 1 条。**真实备份会有 18 条**（见 B-7 实测）。
4. **沙箱 `drill-final` 保留了 756.8 MB**（`--keep`）。确认无需检查后可自行删除；
   另有两个中断的沙箱 `drill` / `drill-b14` 的残留在 `.release-staging/` 下（gitignored）。
5. **备份 `move` 模式要求同卷**，本演练全部在 D 盘，未覆盖跨卷 `copy` 路径
   （该路径由 `test-release.cjs` 的单元测试覆盖）。
6. **27 分钟的摸索**（三次中断）暴露了这台机器的一个特性：**大量小文件的 `rmSync` 极慢**。
   已在脚本里用「拒绝非空沙箱」规避，但后续任何涉及 3 万+ 文件删除的操作都要预留时间。
