## 二、一个被推翻的假设：体积**不是**当前的问题

派单 P5-R6 的触发条件是「单次走查 > 500 MB」。**实测结果远低于此**：

| 量 | 实测值 | 来源 |
|---|---|---|
| 单张 1280×720 PNG | **≈ 77 KB**（13 张累计 1,005 KB） | 现有 6 个 run |
| 双产物单点（A + B + 并排对比，共 3 张） | **214,647 B ≈ 210 KB** | `boot-A-B` / `boot-173955` 实测均值 |
| `report.html` 相对 PNG 的重复开销 | **1.365×**（图片 base64 内联） | 同上 |
| F-12 画面点总量 | **51** | `29-F12-走查用例清单.md` 附录 A |

**推算（假设全部写在 manifest 里，不藏）**：

```
单点 210 KB × 51 点                         = 10.4 MB   （仅 PNG 全帧）
× (1 + 1.365)                               = 24.7 MB   （再算上 report.html 的内联重复）
治理后（假设 70% 点判为一致、降采样到 27%×）  =  5.1 MB
```

> ⇒ **即使按最保守的全帧全 HTML 估算也只有 24.7 MB，远低于 500 MB 阈值。**
> 所以本任务的正确结论是：**不做激进压缩**。治理重心放在「清理策略 + 可定位索引」，
> 压缩只提供**可选**手段并标清代价（有损）。

这不是省事，是**先测量再决策**：如果按派单的风险预设去建一套激进的 PNG 量化流水线，
会为了一个不存在的 500MB 问题牺牲证据保真度。

```jsonc
      "checks": { "A": {"pass":7,"total":8}, "B": {"pass":2,"total":8} },
      "ready":  { "A": true, "B": false },
      "machineVerdict": "failed",
      "verdictNote": "A 检查 7/8；B 未就绪；B 检查 2/8",
      "decisive": true
    }]

```

### 4.1 🔴 关键实现事实：`report.json` 有**两种 schema**

这是在实现中踩到的真问题 —— 第一版解析只认双产物结构，结果 **4 个 run 索引出 0 个画面点**：

| 模式 | 结构 | 出现在 |
|---|---|---|
| 双产物 `--product both` | `{ scenario, results: { A:{...}, B:{...} }, comparisons: [...] }` | `boot-A-B` / `boot-20261016-173955` |
| 单产物 `--product A` | `{ scenario, productId:"A", ..., checks, shots, ... }`（**扁平，无 `results`**） | `catalog-boot-A` / `input-smoke-A` / `save-inject-A` / `boot-20261016-140909` |

> 一个**半空的 manifest 比没有 manifest 更危险**（所有者以为抽查过了）。
> 现已两种都支持，并有用例守住（§八）。

### 4.2 `machineVerdict` 的边界（不冒充裁定）

| 值 | 条件 | 是否决定性 |
|---|---|---|
| `failed` | 任一产物 `ready=false`，或任一 check 为 `pass=false` | ✅ **决定性**（check 失败就是失败） |
| `attention` | checks 全过，但像素差异 > 阈值（默认 2%） | ❌ 需裁定 |
| `consistent` | checks 全过、差异 ≤ 阈值 | ❌ 仍需 E-3 签认 |

> 派单 §三 E-3 ③ 明确：「AI 视觉审阅**不得单独作通过依据**」。
> 因此这里**只输出机器能判的部分**，字段名就叫 `machineVerdict` 而不是 `verdict`，
> 每个点还带 `decisive` 布尔位。最终裁定由 E-3 在证据包上逐条给出。

## 五、体积治理

### 5.1 `prune` —— 清理策略（**默认 dry-run**）

```bash
node tools/evidence-manifest.cjs prune --keep=5 [--protect=boot-A-B]       # 只留最近 5 个
node tools/evidence-manifest.cjs prune --max-mb=200                        # 超限从最旧删
node tools/evidence-manifest.cjs prune --older-than=30                     # 删 30 天前
```

**安全约束（四道，全部有实测）**：

1. 只删 `evidence/` **直接子目录**，名字必须匹配 `^[A-Za-z0-9._-]+$`；
2. 只删「含 `report.json` 或 `A/`/`B/` 子目录」的目录（不像证据包就拒绝）；
3. **绝不删 `manifest.json`**；删除前二次校验 `absDir` 是否越界；
4. `--protect=<runId,...>` 可钉住特定 run（例如作为 O-9b 双产物对比基准的那份）。

排序键：优先 runId 里的时间戳，无时间戳的用目录 mtime —— **并在输出里标注 `⚠ 非标准命名`**，
让操作者知道自己删的是一份「手工命名」的证据。

### 5.2 `compact` —— 降采样（**有损，默认 dry-run**）

规则是一条明确的取舍：

| 点的机器判定 | 处置 | 理由 |
|---|---|---|
| `consistent` | 线性 ÷2 降采样（实测 → **27.3%**） | 像素已基本一致，全帧没有信息增量 |
| `attention` / `failed` | **原样保留全帧** | 那是**需要人看**的证据，降采样等于销毁证据 |

```bash
node tools/evidence-manifest.cjs compact                # dry-run，只报告能省多少
node tools/evidence-manifest.cjs compact --commit        # 真降采样
node tools/evidence-manifest.cjs compact --drop-html --commit   # 再删 report.html（内联重复 1.365×）
```

**实测（6 张 consistent 图）**：`581.1 KB → 158.8 KB`（**27.3%**），单张 94.7KB → 25.2KB。

> `--drop-html` 的理由：`report.html` 把每张图 base64 内联，**内容与 PNG 完全重复**（1.365×）。
> 删掉它不丢信息 —— 图还在，`report.json` 还在，F-16 会从这两者**重建**可复核报告。
> 且降采样后 HTML 里的图与磁盘上的图会不一致，留着反而是「假证据」。

### 5.3 治理决策（当前）：**只部署策略，不执行压缩**

- 现有 6 个 run 共 2.4 MB，**没有压缩的必要**；
- `compact` 的适用时机 = **E-3 完成裁定之后**（那时 `machineVerdict` 才有意义，
  且要确认哪些 evidencia 可以降级）；
- 现在执行 `compact` 会毁掉 E-3 需要的全帧 ⇒ **明确不做**。

## 八、遗留与边界（如实）

1. **4/6 个 run 是非标准命名**（`boot-A-B` 等早期手工产物）。本工具**标记但不改名** ——
   改名会让 F-10 报告与文档里的引用失效。建议：新证据统一用 F-10 默认命名，旧的不追。
2. **`prune` 不区分证据的「价值」**：按时间戳/份数删，可能删掉某个有用的一次性对比。
   → 用 `--protect` 钉住；或干脆不自动清理（当前 2.4 MB 没必要清）。
3. **`compact` 的降采样是简单块抽样（÷2 取左上像素）**，不是面积平均。
   对像素级审阅足够，但**会产生轻微混叠**；若要更高质量需实现 box filter（当前无必要）。
4. **`estimate` 里 70% 判为一致的假设未经实测** —— 必须由 E-3 的真实裁定结果替换。
   在替换前，`5.1 MB` 这个数字只能当**量级**看，不能当承诺。
5. **manifest 在 `evidence/` 内 ⇒ 不会被提交**。若将来需要把某次证据**冻结入库**
   （例如对外发布质量报告），需要另一条路径（导出精简版 manifest + 若干张关键图），当前未做。
6. **未做 PNG 量化/有损编码**。实测不需要（§二），且会牺牲保真度。
   若未来点数暴涨（>200 点或单次 >500 MB）再考虑，方案已写在 §5.2。
