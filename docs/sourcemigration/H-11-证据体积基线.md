## 三、膨胀链路：0.47 MB 的像素 → 21.4 MB 的 JSON（约 **45×**）

以 `f14-healer-both` 为例逐层拆：

| 层 | 动作 | 体积 | 放大 |
|---|---|---:|---:|
| ① 原始 | PNG 截图（已单独落盘） | 0.19 MB | 1× |
| ② 内嵌 | `records[].settle.png` 把 PNG 当 **Buffer → 数字数组** 塞进 JSON | 0.70 MB（紧凑） | **3.7×** |
| ③ 缩进 | `JSON.stringify(..., null, 2)` —— 深层数组每个数字占一整行 | 4.78 MB | **6.8×** |
| ④ 双写 | 同一份 state 又写进 `<P>/result.json` | +4.00 MB | **2×** |
| | **合计** | **9.24 MB** | **≈49×** |

**三层都可以单独砍掉，且都是「调参」不是「换机制」**：

| 改动 | 收益 | 归属 |
|---|---|---|
| `JSON.stringify(o)`（去掉 `,null,2`） | **÷6** | 前端的 `lib/report.mjs` / `lib/runner.mjs` |
| 不把 `settle.png` 序列化进 JSON（PNG 已在外层落盘） | **÷3.7** | 同上 |
| `<P>/result.json` 不重复写 state | **÷2** | 同上 |

> 只做第一项即可把 51 点的总量从 48 MB 压到 23 MB；三项全做 ≈ 7 MB。

## 四、与 B-12 估算的对比（原估算已失效）

| 口径 | 51 点预计 | 偏差 |
|---|---:|---|
| **B-12 第一版估算**（PNG 10.4 + HTML 重复 1.365× = 18.2 MB） | 18.2 MB | **低估 2.6×** |
| **实测口径修正后**（PNG + report.json×51 点 + report.html） | **48.2 MB** | — |
| 若 report.json 紧凑化（缩进 6.0× 归零） | **23.2 MB** | — |
| 紧凑 JSON + compact 降采样（假设 70% 判一致） | 14.0 MB | — |

**为什么原估算会错**：B-12 写在第五阶段，当时 F-10 的格式是「PNG 独立文件 + HTML 内联」；
F-14 换成「catalog records 把 PNG 内嵌进 report.json」后，**主成本项从 PNG 变成了 JSON**。
估算跟着工具走，工具变了估算必须重算 —— 这次就是没跟上。

**⇒ 修正后的 B-12 估算已由工具自动产出**（不再手写死数字）：
`evidence-manifest.cjs build` 的 `estimate.scenarios` 现在给 4 档，basis 里写明
`measuredJsonPerPoint` / `jsonIndentRatio` / `htmlOverPngRatio` 三个实测比值。

### 4.1 给 H-2 的预算线

| 情形 | 预计总量 | 距 P6-R6 阈值（200 MB） |
|---|---:|---|
| 12 个系统各跑 1 次（当前格式，每 run ≈10.7 MB） | **≈128 MB** | 78% —— 接近 |
| 若某些系统分多次跑（51 点 × 双产物）| 可能 **>200 MB** | 🔴 会触发 |

**建议**：H-2 每跑完一个系统就 `build` 一次（增量看 manifest），**总量过 150 MB 立即通知前端**做紧凑化，而不是等到 200 MB 再救。

## 五、🔴 已修：manifest 读不到五态裁定（B-12 自身的缺陷）

### 5.1 现象

F-14 产出证据后，第一次用 `evidence-manifest.cjs build` 索引，结果是**错的**：

```
f14-boot-A2    3 点   c3      ← 判成「3 点一致」
f14-eryou-B2   0 点   -       ← 整 run 不可见
```

而 F-14 自己的裁定是 `pass/unproven` 与 4 条 `blocked`。

### 5.2 根因

五态裁定写在 `results[P].state.catalog.records[]`，**不在 `comparisons` 里**。
而 manifest 只读 `shots[]` + `comparisons[]` ⇒

- **`unproven`（到达证明不足）被记成 `consistent`（一致）** —— 语义**相反**，比"缺数据"更糟；
- **`blocked` 的点没有截图** ⇒ 整个画面点**不进索引**（`f14-eryou-B2` 索引出 0 点）。

这正是 B-12 报告里自己写过的那句话的翻版：**半空的 manifest 比没有 manifest 更危险**。

### 5.3 修法（最小改动，不加能力层）

1. `parseRun` 额外读 `results[P].state.catalog.records[]`（两种 schema 都支持）；
2. 画面点骨架改成 **`shots ∪ comparisons ∪ catalog records`** —— 没截图的 `blocked` 点也要进；
3. **有 catalog 裁定就以它为准**（`verdictSource: "catalog"`），没有才退回原来的 `checks/diff` 推断；
4. 映射表（每条都有理由）：

| F-14 五态 | → machineVerdict | 理由 |
|---|---|---|
| `pass` | `consistent` | 机器判一致，仍需 E-3 签认 |
| `fail` | `failed` | 决定性 |
| `blocked` | `failed` | **产物缺口**，要归账（H-13 / L2/L3） |
| `unproven` | `attention` | **未证明，绝不能算 consistent** |
| `unreachable` | `attention` | 确实到不了，需裁定/挂账 |

5. 体积统计拆成三块（`reportJsonBytes` / `htmlBytes` / `pngBytes`）+ 紧凑化字节。

### 5.4 复验

```
f14-boot-A2    3 点   a1,c2      ← unproven→attention，pass×2→consistent
f14-eryou-B2   4 点   f4         ← 4 条 blocked 全部可见（原来是 0 点）
F-14 五态：pass 2 / blocked 4 / unproven 3
```

回归测试 **23 → 30 项**（新增 7 项：五态映射逐条、blocked 无截图仍在、catalog 优先于 checks、
扁平 schema、旧证据不回归、体积三块）。

## 八、遗留与边界（如实）

1. **H-11 的 ①③ 仍待 H-2**：真实的全量走查还没跑，所以「逐点 manifest 更新」与
   「执行压缩策略」要等 H-2 出数。本报告给的是**基线 + 成本模型 + 预算线**。
2. **`f14-eryou-B2` 只有 0.02 MB**（4 条 blocked、无截图）—— 它说明 `blocked` 的 run 几乎不占体积，
   但**必须被索引**（否则 H-13 归账时找不到它们）。
3. **P6-R6 的 200 MB 阈值**：按当前格式 12 个系统约 128 MB，**不会超**；
   但若 H-2 对某些系统分多次跑（51 点 × 双产物 = 102 次截图），就可能超。已给出预算线与升级路径。
4. **`compact` 对当前格式帮助有限**：它降采样 PNG，而 PNG 只占 6%。**别指望它解决这类膨胀** ——
   先砍 JSON（§六），再用 `compact`。
5. **manifest 里的 `legacy` 命名有 7 个**（f14 run 都是手工 `--out` 命名）。
   不影响使用，但如果 H-2 要按 runId 排序，建议统一用 `<scenario>-<时间戳>`。
