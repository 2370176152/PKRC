## 2. 定位方法（可复现，供 A1/A2 复用）

放弃 v1 依赖的「locales 文件清单」判据，改用**两把硬尺子**：

### 尺子一：构建产物结构签名（判定构建工具链年代）

产物/`.orig` 中可识别构建工具的确定性特征：

| 特征串 | rollup 模式 vite(≤7) | rolldown 模式 vite(8+) |
|---|---|---|
| `const __vite__mapDeps=(i,m=__vite__mapDeps,d=(m.f\|\|(m.f=[...` | ✅ 有 | ❌ 无 |
| `var l=(n,s)=>kOe(n,"name",{value:s,configurable:!0})` | ✅ 有 | ❌ 无 |
| `_mergeNamespaces` 辅助函数 | ✅ 有 | ❌ 无 |
| `l(Class,"Name")` 类名注入点 | ✅ 2540 处 | ❌ 0 处 |
| `=class X extends`（rolldown/oxc 类输出） | 少(1121) | 多(84+) |

> **实测（`.build-tools/analyze-build-sig.py`）**：
> - `tools/game-patcher/backup/loading-scene-By2k7Qfx.js.orig` → **ROLLUP**（`__vite__mapDeps`=5, 注入器=1, `l(...)`=2540）
> - `tools/game-patcher/backup/index-D3KKGO7Y.js.orig` → **ROLLUP**（含 `_mergeNamespaces`=1）
> - 我自建 `90df65097b6d`（vite 8.0.10） → **ROLLDOWN**（`__vite__mapDeps`=0, `l(...)`=0）

### 尺子二：招式数据指纹（判定内容基线年代）

产物中招式构造串形如 `new v(t.MOVE,R.TYPE,B.CAT,power,acc,pp,...)`，可直接与上游 `src/data/moves/move.ts` 的 `new AttackMove(MoveId.MOVE, PokemonType.TYPE, MoveCategory.CAT, power, acc, pp, ...)` **逐字段比对**。

**关键：忽略 PP 字段**——modder 对 PP 做了系统性改动（见 §4），只比 **type/category/power/accuracy** 三个字段，即可锁定上游 commit。

⇒ **唯一自洽解释**：魔改者以**一个 04-24 之前的官方旧树**（vite 7 + 旧 `getPokemonSpecies()` API + 显式 modifier 类）为基底，**手工 backport 后续数据改动**（06-08 平衡等），并叠加自己的 6 大系统 + 7 补丁。

**这彻底否决了"复现 `.orig` 字节"的可行性**，原因有三且相互独立：
1. base 是一个**我们无法定位精确 commit 的 04-24 前私有树**；
2. base 被**手工改动**过（并非任何官方 commit 的快照）；
3. 即便拿到 base，工具链与构建确定性差异也会导致字节不同。

**A1 判据正式改写（替代"hash 对齐"）：**

| 编号 | 判据 | 可证伪方式 |
|---|---|---|
| A1.1 | **构建可复现**：锚点树 + 锁定 lockfile + node24/pnpm10.33.2，连续两次产物 entry-chunk hash 一致 | 两次 hash 比对 |
