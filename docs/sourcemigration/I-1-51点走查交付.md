## 四、🔴 过程中发现的 3 个 P0（B 此前从未成功启动）

**这是 I-1 最重要的产出**：走查一开跑就发现「产物 B 根本起不来」，而 tsc / vite build 全绿。

| # | 报错 | 根因 | 修法 |
|---|---|---|---|
| 1 | `ReferenceError: safeT is not defined`<br>@`createAttackTalent` | 悬空 `declare`，但 `TALENT_POOL` 在**模块求值期**就调用它 | 实现产物 `es`：`i18next.t(key,def)`，空串回退 |
| 2 | `TypeError: FixedBattleConfig is not a constructor` | **循环导入**：<br>`battle → modifier → pt-soudache-system → title-phase → game-mode → fixed-battle-configs → battle` | ① `TitlePhase` 改 `pushNew("TitlePhase")` 断边<br>② 守门员数据表拆到零副作用的 `pt-guardian-data.ts` |
| 3 | `ReferenceError: createSpeciesPartyWeightModifiers is not defined`<br>@`createMarowakThickClubTalents` | 同 1，且**启动路径调用**（`initializeTalentSystem → getTestTalents → …`） | talent 剩余 6 项 declare 全部实现（`KN`/`Rre`/`xNe`/`Lue`/`Dse`/`I0`） |

**实测对比**：

| | 修前 | 修后 |
|---|---|---|
| A 就绪 | 4836ms | 4836ms |
| **B 就绪** | **30s 超时，纯黑屏（stdDev=0 / distinctColors=1）** | **11627ms（stdDev=25.57）** |

### 方法论修正（必须写进后续批次）

> 🔴 **「declare 悬空」有两种爆炸形态，静态扫描只能抓第一种。**
> ① **模块求值期调用** ⇒ import 时立刻 `ReferenceError`（AST 扫描可抓）
> ② **启动路径调用** ⇒ `initializeXxx()` 跑起来才崩（**只能真跑暴露**）
>
> ⇒ **`tsc` 过 / `vite build` 过 / 静态闸门过，都不能替代「真跑一次」。** 这正是前六个阶段反复推迟走查的代价。
