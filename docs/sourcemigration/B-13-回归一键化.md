## 三、🔑 最重要的设计：每条套件钉死它自己的 Node

本项目同时存在**三个** Node（运行期 16.16.0 / 构建期 24.9.0 / 走查期 ≥22）。
「随便找个 node 跑全部」是本工具最容易犯、也最有害的错误 —— 那样它只能证明「某处能跑」。

| 套件 | 解释器 | 为什么必须是它 |
|---|---|---|
| 服务层 | `shared/runtime/node.exe`（**16.16.0**） | 契约是「跑在**运行期 Node 16** 上」。用 Node 24 跑会**测不出** Node 16 语法问题（例如误用 `findLast` / `structuredClone`），而那正是玩家侧会崩的地方 |
| 输入层 | node **≥22** | `run-tests.js` 是 ESM（`import`）——Node 16 直接 `SyntaxError: Cannot use import statement outside a module`（实测 EXIT=1） |
| 其余 6 套 | `shared/runtime/node.exe`（16.16.0） | 用**最严格的语法上限**跑，任何工具一旦写了 Node 17+ 语法就会被立刻抓住 |

**≥22 的解释器怎么找**：`[process.execPath, .build-tools/node-v24.9.0-win-x64/node.exe]` 里取第一个
major ≥ 22 的。都找不到 ⇒ 该套件判 `error` 并**整体非零退出**（并给出可操作提示），
绝不静默跳过 —— 跳过等于假装验证过。

## 四、四态判定（不只是「非零退出」）

| 状态 | 条件 | 为什么需要 |
|---|---|---|
| `pass` | exit 0 **且** 项数 ≥ `min` | 正常 |
| `fail` | exit ≠ 0 | 基础 |
| `shrink` | exit 0 **但项数 < min`** | **防静默删测试**：把某个 `it()` 注释掉、或 `describe.skip`，exit 仍然是 0。没有这一档，回归门禁会一年年变松而无人察觉 |
| `error` | 入口不存在 / 缺解释器 / 无法 spawn / 超时 | 基础设施问题不能伪装成「通过」 |

**`min` 的口径**：只作**下限**。新增测试不必改这个数字；**删测试必须改，并说明理由**。
（这也是为什么上表要逐套件列出实测项数。）

**故意不误报**：输出格式变了导致项数**解析不出来**时记 `count: null`、判 `pass`,
不判 `shrink` —— 否则一次无关的文案改动就会让门禁误红。

## 八、遗留与边界（如实）

1. **`spawnSync` 依赖**：本环境实测可用（`status` 正确回传）。若将来沙箱禁 spawn，
   工具会明确报 `无法启动子进程：EBUSY` 并判 `error`，**不会伪装成通过**。
   备选方案（进程内 `require` 各套件）**故意没做** —— 各套件自带 runner 并设 `process.exitCode`，
   进程内跑会互相污染，且拿不到真实耗时。
2. **`min` 是静态数字，需要人工维护**。新增测试不管（只作下限），**删测试必须同步改**。
   这是有意的摩擦：让「少测了几项」这个动作必须留下痕迹。
3. **32s 的耗时主要来自发布脚本**（3 次全量合并）。若日后想快，应该优化
   `test-release.cjs` 的夹具规模，而不是把 `release` 从门禁里拿掉。
4. **不覆盖 F-10 走查与 `tsc`/`vite build`**：本工具只跑**仓内测试套件**。
   构建回归（`tsc` 0 错、`vite build` EXIT=0）属 E-2/E-6 的另一条线，
   需要构建期 Node 与锚点树，不应塞进这个门禁里（会让它从 40s 变成 3min+）。
5. **契约五项与实测的 9 项差额（§二）需要 E-6 知情**，否则会被误判为回归。
