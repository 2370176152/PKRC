## 二、双模甄别与复用率实测

### 2.1 反查基座

| 项 | 值 |
|---|---|
| 反查范围 | 改版产物 `game/server/dist/locales/zh-CN/` **全部 64 个命名空间文件** |

| 归一化骨架 | 8,259 个（`${x}`/`{{x}}` → `{}`） |

### 2.2 双模策略

| 模 | 规则 | 命中记 |
|---|---|---|
| **exact** | 文本完全相等 | `match_mode: "exact"` |
| **skeleton** | 插值归一化后相等（`刷新 (${cost}PT)` ≡ `刷新 ({{cost}}PT)`） | `match_mode: "skeleton"` |

骨架匹配命中 5 条（B1），样本：

| 产物行 | manifest 文本 | 复用目标 |
|---|---|---|
| L2 | `已达刷新上限 (${wg}/${wg})` | `talent:shop.maxRefreshReached` |
| L443 | `已达刷新上限 (${this.refreshCount}/${this.maxRefreshCount})` | `talent:shop.maxRefreshReached` |
| L443 | `第${O.acquiredWave}层获得` | `talent:viewer.acquiredWave` |
| L443 | `${s+1}-${i}/${this.acquiredTalents.length} (↑↓滚动)` | `talent-codex:scrollHint` |
| L1036 | `${ie(s)}\n受到了${this.type.name}的伤害！` | `battler-tags:saltCuredLapse` |

### 2.3 🔴 为什么复用率只有 9.8%（U-2 估计的证伪）

U-2（10-14）估 B1~B3 可复用 ~500 条（B1 ~360 / B2 ~50 / B3 ~90）。**实测 245**（148/30/67）。逐项核对：

| 批次 | U-2 估计 | 实测 | 差 | 原因 |
|---|---:|---:|---:|---|
| B1 | ~360 | 148 | -212 | 估计按「天赋 UI 层」推；实测 manifest 扫出的 TALENT 文案**大头是 TalentRegistry 校验 / AI 决策日志 / 战斗播报**（L2/L378/L1011），UI 层 talent.json 只有 61 条真重叠 |
| B2 | ~50 | 30 | -20 | 命之座纯改版新增，本就无存量；30 条命中均为 pokemon-info 等通用属性名 |
| B3 | ~90 | 67 | -23 | 接近估计；modifier-type(39) / berry(11) 是主力来源 |

**结论**：manifest 的扫描源（`loading-scene-*.js`）承载的是**逻辑层**文案，而现有 locales 是**界面层**文案。两层分工不同、文本不重叠是**架构事实**，不是甄别遗漏。**B4~B6 的复用预期应按 10% 量级修正**（B0 的 1/24 是第三种情况：与上游 common.json 的词表级重叠）。

### 2.4 manifest reuse 标记质量（与 B0 对比）

| 批次 | 标记 reuse | 实测命中 | 虚标 | 准确率 |
|---|---:|---:|---:|---:|
| B0（COMMON，上批） | 29 | 1 | 28 | **3%** |
| B1 | 209 | 148 | 0 | **100%**（去重后全部命中） |
| B2 | 40 | 30 | 0 | **100%** |
| B3 | 87 | 67 | 0 | **100%** |

> B1~B3 的标记在**同系统内**做判断（天赋文案 vs talent.json），故准；B0 是**跨上游词表**判断（通用词 vs common.json 8,679 条），故虚。**B4~B6a 属前者（可信），B6b 属后者（须独立甄别）**。

## 三、key 命名约定（行号锚定）

**新 key 形如 `L<产物行号>_<行内序号>`**：

```json
{
  "L2_1": "天赋ID不能为空",
  "L2_2": "天赋名称不能为空",
  "L2_3": "简短描述不能为空",
  "L336_1": "剧毒"
}
```

**为什么不用语义 key**（2,066 个语义 key 的代价）：

| 方案 | 问题 |
|---|---|
| 语义 key（如 `talentRegistry.idEmpty`） | ① 2,066 条人工命名不可行；② 重名消歧逻辑复杂；③ 命名错误反而误导 |
| **行号锚定（本批采用）** | ① 机器生成零冲突；② **溯源明确**（key 直接告诉你产物哪一行）；③ S7-4 施工时按行号定位文本、替换为 `t()` 调用，**零歧义**；④ 可随时改语义 key（改 JSON + 调用点 + mapping 三处同步即可，mapping 的 `key` 字段是唯一权威） |

**行号分布**（施工时按行聚集替换，效率最高）：

| 批次 | 行数 | 行号 |
|---|---:|---|
| B1 | 32 | 2,334,342,346,347,367,371-374,378,392,396,400,412,441-443,447,448,450,453,472,998,1011,1015,1017,1020,1031,1033,1036,1038 |
| B2 | 10 | 332,354,397,436,454,456,466,467,996,1025 |
| B3 | 11 | 336,338,340,341,358,364-366,402,468,1028 |

## 四、插值转换待办（801 条）

manifest 的 dynamic 文本保留**产物原始 `${...}` 形态**（与产物一致，diff 走查要比对），mapping 已逐条提取 `interp_vars`：

```json
{
  "line": 442, "kind": "dynamic",
  "text": "确定要刷新天赋商店吗？\n消耗 ${this.refreshCost}PT，剩余次数 ${s}/${this.maxRefreshCount}。刷新后当前天赋将消失！",
  "key": "L442_1", "action": "new",
  "interp_vars": ["this.refreshCost", "s", "this.maxRefreshCount"],
  "needs_interp_convert": true
}
```

| 批次 | 插值记录 | 说明 |
|---|---:|---|
| B1 | 595 | 全线最大宗；多为 `this.xxx`（类成员）与 `n.name`（对象属性），S7-4 定名时注意与调用处变量对齐 |
| B2 | 115 | 含 `${r.ivs.join(", ")}` 等**表达式插值**——需先在调用处算好再传参 |
| B3 | 91 | 同上 |

**S7-4 转换规则**（已定，施工照做）：`${expr}` → `{{varname}}`，JSON value 与调用点 `t(key, {varname: expr})` 同步改；**变量名由 S7-4 定**（本批只列 `interp_vars` 原始表达式）。

### 6.2 mapping 记录字段

| 字段 | 含义 |
|---|---|
| `line` / `kind` / `text` / `len` / `system` | 与 manifest 逐字段一致（对账锚） |
| `key` | 本批 key（新建 = `L行_序`；复用 = 现有全限定 key如 `talent:shop.refresh`） |
| `action` | `new` / `reuse-existing` / `batch-internal-reuse` |
| `match_mode` | `exact` / `skeleton`（仅 reuse-existing） |

| `manifest_reuse` | manifest 原标记（用于标记质量核对） |
| `interp_vars` / `needs_interp_convert` | 插值变量清单 / 是否需转 `{{}}` |
| `cross_batch` | 跨批重复标注 |
