# PKRC 改造 v2 · 源码化优先版（重构方案）

> **决策变更**：项目所有者决定——**出于维护性与可修改性考虑，先完成源码化**，并**将源码化整体交付给全栈工程师**。
> **本方案性质**：对 `docs/delegation/**`（v1，产物优先）的**完整重构**，产出 v2 分工 + 看板 + 甘特图。
> **编制日期**：2026-10-13
> **知识截止 2026-09-07**（联网核验执行于 2026-10-13）

---

# 零、决策变更的连锁影响（先看这个）

## 0.1 一句话概括变化

> **工作基底从「不可重建的 Vite 产物」变成「可构建的上游 TS 仓库」。**

这**反转了整个项目的依赖方向**：

| | v1（产物优先） | **v2（源码化优先）** |
|---|---|---|
| **起点** | S0 运行时钩子补丁 | **S1 上游 fork + 构建复现** |
| **改代码的方式** | 字符串补丁 + 外置 ESM 层 | **直接改 TS 源码** |
| **`pkrc/**` 外置层** | 主体交付物 | **降级为过渡产物 / 大部分作废** |
| **补丁工具** | 核心机制 | **归档（⚠️ 见 §3.4）** |
| **源码化** | 长期可选项（S8） | **项目起点（S1）** |
| **输入层/视觉改造** | 在产物上做 | **在源码上做（更简单、更彻底）** |

## 0.2 ⚠️ 关键技术判断：源码化让大量工作**变简单**，但**不是**简单平移

**这是本方案最重要的一节，请全栈务必读完。**

v1 计划里的输入层与视觉改造之所以设计得那么复杂（外置层 + 运行时归一 + 锚点钩子），**根本原因是"产物不可重建"**。源码化后这层约束消失：

| v1 的做法（产物上） | v2 的做法（源码上） | 简化程度 |
|---|---|---|
| 108 处裸字号**运行时归一** | 直接改 `src/**` 里的字号常量 | 🟢 **大幅简化** |
| 30+ 处 pointerdown **外挂重写** | 直接在源码里规范化 | 🟢 **大幅简化** |
| 1808 条中文**外置 i18n 抽取** | 改为 `i18next.t()` 调用 | 🟡 仍需做，但更自然 |
| 输入层**外置 ESM + 桥接** | 在源码里新建 `src/input/**` 模块 | 🟢 **大幅简化** |
| 运行时钩子 `window.__PKRC__` | **完全不需要** | 🟢 **直接删掉** |

**但有一个前提**：**魔改点必须先成功迁移到源码**，否则源码构建产物 ≠ 现有发行版。

**结论**：
- v1 的**设计洞察**（7 个耦合点、覆盖矩阵、Token 体系、AGPL 判定）**全部保留**，作为"改造需求规格"
- v1 的**实现方案**（外置层、运行时钩子、运行时归一）**大部分作废**
- 输入层/视觉改造的**执行方式**从"产物外挂"改为"源码直改"

## 0.3 🔴 新发现：魔改点定位问题比预期**简单得多**

**实测**（`loading-scene-By2k7Qfx.js`）：

```bash
grep -o -E 'l\([a-zA-Z0-9_$]+,"[A-Za-z][A-Za-z0-9_]*"\)' loading-scene-By2k7Qfx.js | wc -l
# → 2639
```

> **产物压缩后仍保留了 2,639 处类名字符串**（`l(Class,"ClassName")` 形式，来自 Vite 的 `keep_classnames` / TS `emitDecoratorMetadata` 类保留）。

**这意味着**：
- **每一个上游类都能用它的名字字符串在产物中定位** → 反查对应源码文件
- 现有 7 条补丁的描述里**已经写明了上游类名**（`TeraStarstormTypeAttr` / `TeraMoveCategoryAttr` / `DefaultOverrides` / `PT_SOUDACHE`）

**已核实的上游源码路径**（联网核验 2026-10-13）：

| 补丁 | 上游类名 | 上游源码文件 |
|---|---|---|
| `tera-starstorm-type` | `TeraStarstormTypeAttr` | `src/data/moves/move.ts` |
| `tera-move-category-attr` | `TeraMoveCategoryAttr` | `src/data/moves/move.ts` |
| `nihil-light-category` | `allMoves` 里的 `NIHIL_LIGHT` | `src/data/moves/move.ts` |
| `stellar-multiplier-fixed` | `PokemonType` 倍率逻辑 | `src/field/pokemon.ts` |
| `pt-save-import-allow` | `DefaultOverrides` | `src/overrides.ts`（待确认） |
| `pt-save-import-gamemode-literal` | `PT_SOUDACHE`（魔改枚举） | 魔改新增 |

**这对 C-4（魔改点迁移）成本的影响**：

> C-4 从「研究项目」降级为 **「半机械化提取」**。可写脚本批量提取 2,639 个类名 → 反查上游文件 → 生成映射表初稿。

# 第一部分　角色重新分配

## 1.1 v2 分工总表

| 角色 | v1 职责 | **v2 职责（重构后）** | 变化幅度 |
|---|---|---|---|
| **全栈** | S0 + S1外壳 + S7 | 🔴 **上游 fork 全权负责**：构建复现 + 魔改点迁移 + 产物切换 + **以及后续在其源码上做输入层/视觉改造的技术底座** | 🔥 **暴涨** |
| **前端** | S2/S3/S4（产物外挂） | 🟡 **改为「源码上实现输入层规范化」**：在 TS 源码里重构交互层（需求规格沿用 v1） | 方式变，目标不变 |
| **后端** | S1服务层 + S8 | 🟢 **基本不变**：服务层（server.cjs/日志）+ 源码化收尾（资产管线/发布脚本） | 微调 |
| **UI** | S5/S6（产物外挂） | 🟡 **改为「源码上实现视觉 Token 体系」**：改 TS 源码的文本创建与样式 | 方式变，目标不变 |

## 1.2 🔴 核心变化：全栈成为**唯一的关键路径起点**

```
v1：全栈 S0 ──┬─→ 前端 S2→S3→S4
              └─→ UI  S5→S6

v2：全栈 S1（源码化）
      ├─→ 产出「可构建的上游仓库」  ← 【全体下游的新工作基底】
      │
      └─→ 前端 S2'（源码输入层）──┐
          UI   S3'（源码视觉层）──┴─→ 集成验证 → 发布
          后端 S4'（服务/资产/发布）
```

**全栈的 S1 是硬前置**：在它交付「可构建 + 魔改完整迁移」的仓库之前，**前端与 UI 无法开始**（因为他们的工作对象变了）。

## 1.3 全栈的职责边界（本次最关键的定义）

### ✅ 全栈做

| 阶段 | 任务 |
|---|---|
| **A0 上游定位** | 锁定上游版本（已初判 v1.11.x / 2025-06~08）+ clone + 确认 commit |
| **A1 构建复现** | pnpm + Node 22 + 拉 locales submodule + baseline 构建 + 与官方 release 比对 hash |
| **A2 魔改点提取** | 用 2,639 类名映射 + 现有 7 条补丁 + 产物扫描 → 产出完整魔改点清单 |
| **A3 魔改迁移** | 把魔改点逐条落到 TS 源码（新增模块 / 修改现有） |
| **A4 等价性验证** | 构建产物 vs 现有发行版逐项功能比对 |
| **A5 产物切换** | 新构建产物替换 `game/server/dist/` |
| **A6 技术底座交接** | 给前端/UI 交接「如何在源码上开发」的工程规范 |

### ❌ 全栈不做（他人负责）

| 事项 | 归属 |
|---|---|
| 输入层重构的具体实现 | 前端 |
| 视觉 Token 体系的具体实现 | UI |
| 服务层 / 日志 / 发布脚本 | 后端 |
| 存档兼容性验证 | 后端 + 全栈联合 |

### ⚠️ 全栈的**最大风险**

| 风险 | 说明 | 应对 |
|---|---|---|
| **A3 魔改迁移不完整** | 魔改是**深度嵌入**的（实测 `ERYOU` 17 处、`JIEMING` 9 处、`TALENT` 11 处），不是浅层补丁。遗漏 = 功能丢失 | **A4 等价性验证必须逐项**，不能抽样 |
| **上游代码结构演进** | 新式上游已改用 `#app/` `#data/` alias 与新目录（`src/data/moves/move.ts`）。**本仓库产物无 alias 保留 → 确认是旧构建风格** | 严格锁定版本，不要用最新上游 |
| **6 大自研系统全在压缩产物里** | 天赋/命座/解明/二游/PT/P5X 的**源码不存在**，只有产物 | **必须从产物反推还原 TS 源码** —— 这是 A3 最大的工作量 |

## 2.1 阶段总表

| 阶段 | 名称 | 主责 | 前置 | 可交付物 |
|---|---|---|---|---|

## 2.2 关键变化：**依赖链拉长了，但每步更确定**

| | v1 | v2 |
|---|---|---|
| 前端/UI 等待时间 | 等 S0（约 1 步） | **等 S5（约 5 步）** ⚠️ |
| 但换来 | 产物上的将就方案 | **源码上的彻底方案** |
| 风险性质 | chunk 哈希失效（持续性） | 魔改迁移不完整（一次性） |

> **这是本次决策的真实代价：前置期变长。**
> **但收益是：从"永远在和产物搏斗"变成"一次性把地基打好"。**
> 用户选择「出于维护性与可修改性考虑」——这个权衡是正确的。

## 2.3 并行机会（尽量压缩前置期）

虽然 S6/S7/S8 都依赖 S5，但**部分工作可以提前**：

| 可提前的工作 | 谁 | 为什么能提前 |
|---|---|---|
| **输入层需求规格**（v1 的 7 耦合点 + 覆盖矩阵） | 前端 | 纯设计，已由 v1 派单 02 产出 ✅ |
| **视觉 Token 体系**（v1 的 7 级字号 + 映射表） | UI | 纯设计，已由 v1 派单 04 产出 ✅ |
| **服务层改造**（`server.cjs` 工厂化 + 日志） | 后端 | **与产物无关**，可立即开工 ✅ |
| **i18n 命名空间设计 + 1808 条文案清点** | UI | 文案在 `dist/locales` 与产物里，可先清点 ✅ |
| **发布/资产管线脚本设计** | 后端 | 纯设计 |
| **魔改点提取脚本**（用 2,639 类名） | 全栈 | S1 之后即可 |

> **调度建议**：让前端/UI/后端在 S1–S5 期间完成**所有纯设计工作**，S5 一到就进入实现——把前置期的浪费降到最低。

## 6.3 S2 的起点：用 2,639 类名做提取

```bash
# 从产物提取全部类名（这是 A2 的核心工具）
grep -o -E 'l\([a-zA-Z0-9_$]+,"[A-Za-z][A-Za-z0-9_]*"\)' \
  game/server/dist/assets/loading-scene-By2k7Qfx.js \
  | sed 's/.*,"\(.*\)")/\1/' | sort -u > /tmp/classnames.txt

wc -l /tmp/classnames.txt     # → 2639

# 逐个在上游源码中定位
while read name; do
  grep -rl "class $name" upstream-pokerogue/src/ 2>/dev/null | head -1 | sed "s|^|$name → |"
done < /tmp/classnames.txt > /tmp/classname-to-file.map
```
