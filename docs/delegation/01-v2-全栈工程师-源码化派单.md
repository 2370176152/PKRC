## 二、🔴 最大的挑战：6 大自研系统**没有源码**

**实测证据**（`loading-scene-By2k7Qfx.js`）：

| 魔改系统               | 产物内出现次数    |
| ------------------ | ---------- |
| `ERYOU`（二游养成）      | 17         |
| `TALENT`（天赋）       | 11         |
| `JIEMING`（解明）      | 9          |
| `PT_SOUDACHE`（搜打撤） | 7          |
| `SOUDACHE`         | 7          |
| `MINGZUO`（命之座）     | 0（可能用其他标识） |

**这意味着**：

> 天赋 / 命之座 / 解明 / 二游养成 / PT搜打撤 / P5X战斗 —— 这 6 大系统**在产物里是压缩代码，在上游里不存在**。  
> **你必须把它们从产物反推还原为 TS 源码。**

**这是 A3 阶段的主体工作量，也是本项目的最高风险（V1）。**

### 6 大系统的还原策略

```
第 1 步：能力识别（低成本）
  └─ 用标识符（ERYOU/TALENT/JIEMING/PT_SOUDACHE）在产物中定位所有相关代码块
  └─ 用类名字符串（l(Class,"XxxAttr")）定位相关的类定义

第 2 步：依赖分析（中成本）
  └─ 找出每个系统依赖了哪些上游模块（存档字段、UI handler、枚举）
  └─ 这决定了它在源码里应该挂在哪里

第 3 步：逐系统还原（高成本）
  └─ 按优先级排序（建议：用户实际使用频度）
  └─ 每还原一个，单独构建验证（增量交付）

第 4 步：接入上游结构（中成本）
  └─ 复用上游的 UI handler / 存档 / 枚举体系
  └─ 不要自造平行体系（否则将来合并上游会持续冲突）
```

**优先级建议**（可按实际使用频度调整）：

```
1. PT 搜打撤（有 2 条现有补丁，且涉及存档导入 → 影响最大）
2. 天赋（有 i18n 文件，结构最清晰）
3. 二游养成（出现次数最多，17）
4. 解明（9）
5. 命之座
6. P5X 战斗
```

## 三、🔑 你手里的钥匙：2,639 个类名

**实测**：

```bash
grep -o -E 'l\([a-zA-Z0-9_$]+,"[A-Za-z][A-Za-z0-9_]*"\)' loading-scene-By2k7Qfx.js | wc -l
# → 2639
```

产物压缩后**仍保留了 2,639 处类名字符串**（`l(Class,"ClassName")`）。

**为什么这很重要**：产物把 `class TeraStarstormTypeAttr` 压缩成了 `class dZ`，但保留了 `l(dZ,"TeraStarstormTypeAttr")` —— **类名没丢**。

**双重收益**：

1. **定位魔改点**：凡是在产物有类名、但上游找不到的 → **必是魔改新增**
2. **定位上游落点**：凡是在上游能找到的 → **直接得到源码文件路径**

**现有 7 条补丁已经证实了这条路可行**——补丁描述里直接写了类名：

| 补丁 id                      | 上游类名                       | 上游文件（已核实）                |
| -------------------------- | -------------------------- | ------------------------ |
| `tera-starstorm-type`      | `TeraStarstormTypeAttr`    | `src/data/moves/move.ts` |
| `tera-move-category-attr`  | `TeraMoveCategoryAttr`     | `src/data/moves/move.ts` |
| `nihil-light-category`     | `allMoves` 内 `NIHIL_LIGHT` | `src/data/moves/move.ts` |
| `stellar-multiplier-fixed` | 属性倍率                       | `src/field/pokemon.ts`   |
| `pt-save-import-allow`     | `DefaultOverrides`         | `src/overrides.ts`（待确认）  |

> **注**：路径基于 2026-10-13 检索的上游文档。上游已改用 `#app/` `#data/` alias 与新目录（`src/data/moves/move.ts`），而**本仓库基线是旧风格**（产物无 alias 保留）→ **实际路径以你锁定的 commit 为准**。

## 四、阶段任务

### A0　上游定位

**目标**：锁定确切的上游 commit。

**已知**：版本区间 **v1.11.x（2025-06~08）**，依据是 locales 命名特征（见 `06-源码化与其他技术决策.md` §1.2）。

```bash
git clone --filter=blob:none https://github.com/pagefaultgames/pokerogue.git upstream-pokerogue
cd upstream-pokerogue

# 用 locales 命名定位（本仓库是 zh-CN/zh-TW，上游 2025-10 后改为 zh-Hans/zh-Hant）
git log --oneline --diff-filter=R -- '*zh-CN*' | tail -5

# 逐候选版本比对 locales 清单
ls public/locales/                                    # 应为 17 个
diff <(ls public/locales/) <(ls ../../game/server/dist/locales/)
```

**验收**：记录 commit hash + 版本号 + locales 清单一致性。

### A1　构建复现

**目标**：在不含魔改的 baseline 上成功构建，验证管线正确性。

**上游要求**（已核验）：

- **pnpm**（2025-06 由 npm 迁移）
- **Node 22**
- locales 是**外置 git submodule** → 需 `--recurse-submodules`

```bash
corepack enable && corepack prepare pnpm@latest --activate
pnpm install                    # 含 submodule
pnpm build
sha256sum dist/assets/index-*.js    # 与上游官方 release 比对
```

**⚠️ 关键判据修正**（v1 计划书的错误）：

> 计划书要求「产物 hash 与**现发行版**对齐」—— **这是错的**。现发行版含魔改，hash 必然不同。  
> **正确判据是两段式**：
>
> ```
> 阶段 1：baseline（无魔改）构建 → hash 对齐【上游官方 release】  ← 验证管线
> 阶段 2：叠加魔改 → hash 变化                                  ← 预期行为
> ```

**验收**：baseline hash 与上游官方 release 一致（若不一致 → 先排查环境，**不要继续**）。

### A2　魔改点提取（清单化）

**目标**：产出**完整的**魔改点清单，每条含「上游文件映射」。

**三个输入源**：

| 源              | 内容                                                           |
| -------------- | ------------------------------------------------------------ |
| **① 现有 7 条补丁** | `tools/game-patcher/patch-game.py` 的 `PATCHES` —— 描述文字里有上游类名 |
| **② 2,639 类名** | 产物提取 → 上游源码反查                                                |
| **③ 产物扫描**     | 用 `ERYOU`/`TALENT`/`JIEMING`/`PT_SOUDACHE` 等标识定位系统           |

```bash
# 提取全部类名
grep -o -E 'l\([a-zA-Z0-9_$]+,"[A-Za-z][A-Za-z0-9_]*"\)' \
  game/server/dist/assets/loading-scene-By2k7Qfx.js \
  | sed 's/.*,"\(.*\)")/\1/' | sort -u > classnames.txt

# 逐个在上游定位
while read name; do
  f=$(grep -rl "class $name" upstream-pokerogue/src/ 2>/dev/null | head -1)
  echo -e "$name\t${f:-【上游无→魔改新增】}"
done < classnames.txt > classname-to-file.map

# 分类统计
grep -c "魔改新增" classname-to-file.map     # 魔改独有类数量
grep -vc "魔改新增" classname-to-file.map    # 上游已有类数量
```

**产出**：`魔改点清单.md`，每行：

```
魔改点 | 类型(新增/修改) | 产物位置 | 上游文件 | 说明 | 来源(补丁/扫描)
```

**验收**：清单覆盖 ① 全部 7 条补丁 ② 6 大自研系统的全部入口 ③ 3 类视觉改动（字号/pointerdown/文案）。

### A3　魔改迁移（**主体工作量**）

**分类处理**：

| 魔改类型                                           | 迁移方式             | 难度   |
| ---------------------------------------------- | ---------------- | ---- |
| **新增模块**（天赋/命座/解明/二游/PT/P5X）                   | 从产物还原为 TS，挂到上游结构 | 🔴 高 |
| **修改现有**（招式属性、倍率、游戏模式）                         | 直接改对应 TS 文件      | 🟢 低 |
| **枚举扩展**（`PT_SOUDACHE=10`、`PokemonType.CS=19`） | 改 `src/enums/**` | 🟢 低 |

**⚠️ 硬约束**：

- **不得改动存档序列化与加密**（风险 V7）
- **不得自造平行体系**——复用上游的 UI handler / 存档 / 枚举（否则将来合并上游持续冲突）
- **逐个系统增量交付**，每完成一个就构建验证（不要憋到最后）

**验收**：源码含全部魔改，构建通过。

## 九、关键假设清单

1. **假设** 上游 v1.11.x 与现有产物结构匹配（依据 locales 命名特征）—— A1 的 hash 比对会验证。
2. **假设** 2,639 类名中，上游找不到的即为魔改新增 —— 需人工复核，可能有重命名的情况。
3. **假设** 6 大自研系统可从产物还原为可维护的 TS —— **这是本方案最大的不确定性**；若某系统还原成本过高，可**降级为"功能保留 + 标记待重构"**。

5. **假设** 魔改未改动存档序列化 —— 若有改动，需单独处理（V7）。

> 假设不成立时**先更新本文档与 `08-v2源码化优先-重构方案.md`**，再改代码。
