# 第一部分　源码化深度评估（S8）

## 1.1 一个必须先说的前提：AGPL-3.0 的法律义务

**实测证据**（仓库根 `LICENSE` + `NOTICE.md`）：

```
上游项目：pagefaultgames/pokerogue
许可证：GNU Affero General Public License v3.0（AGPL-3.0）
```

**AGPL-3.0 第 1 条对「Corresponding Source」的定义（LICENSE 第 122–141 行原文）**：

> The "Corresponding Source" for a work in object code form means **all the source code needed to generate, install, and (for an executable work) run the object code and to modify the work**...

**这意味着**：

| 现状 | AGPL 义务 | 判定 |
|---|---|---|
| 分发编译后的 `dist/` 产物 | 必须同时提供**生成该产物的完整源码**（含构建脚本） | ❌ **当前不满足** |
| 魔改后的产物 | 魔改部分的源码也必须提供 | ❌ **当前不满足**（魔改逻辑藏在压缩 chunk 里，无法作为"源码"交付） |
| 本次「锚点补丁 + 外置模块层」 | 外置层有源码 ✅，但**7 条补丁修改的产物部分仍无源码** | ⚠️ **部分满足** |

**关键判断**：

> **「产物即源码」不只是工程问题，更是许可证合规问题。** 计划书 §1.3 把源码化列为「长期可选优化」，但按 AGPL-3.0 口径，它是**分发行为的前置合规条件**。

**两个务实选项**：
- **选项 α（推荐）**：S8 源码化立项，作为合规基线。同时把外置层 `pkrc/**` 以源码形式随包发布（这部分已经合规）。
- **选项 β**：若本仓库仅**内部使用 / 不分发**（AGPL 第 13 条针对网络交互，不涉及则义务较轻），则当前状态风险可控；但**一旦对外分发产物**，必须走 α。

**待确认**：本仓库是否对外分发？——**这个答案决定 S8 的优先级是「长期」还是「紧急」**。

## 1.2 上游版本对齐（原 C-1）—— ✅ 已取得**可执行结论**

计划书说「版本时间戳不一致，无法对齐」。**实测发现上游版本是可以锁定的**，靠一个强特征：

### 关键证据：语言目录命名是版本分水岭

**实测**（`game/server/dist/locales/`，17 个目录）：

```
ca-ES  da  de  en  es-ES  fr  he  it  ja  ko  pt-BR  ro  ru  th  tr  zh-CN  zh-TW
```

**上游 locales 仓库的命名演进（联网核验，2026-10-13 检索）**：

| 时期 | 中文语言标识 | 语言数量 | 依据 |
|---|---|---|---|
| 2025-06 及之前 | `zh-CN` / `zh-TW` | 17 个 | `iTunesko/pokerogue-locales` 快照（2025-06-07）：ca-ES/da/de/en/es-ES/fr/he/it/ja/ko/pt-BR/ro/ru/th/tr/**zh-CN**/**zh-TW** —— **与本仓库完全一致** |
| 2025-08 | 过渡期 | 出现 `es-MX` → `es-419`、新增 `tl` | `ALLiDoizCode` 快照（2025-08-26）：仍有 `zh-CN/zh-TW`，但已新增 `tl` |
| 2025-10 之后 | **`zh-Hans` / `zh-Hant`** | 新增 `nb-NO`、`sv` 等 | `Bertie690` 快照（2025-10-18）已改名；`pagefaultgames` 主线（2026-01）为 `zh-Hans/zh-Hant` |

**判定**：

> **本仓库的上游基线锁定在「`zh-CN/zh-TW` 尚未改名 + `tl` 尚未加入」的窗口内 → 即 2025-06 ~ 2025-08 之间，对应上游 v1.11.x 世代。**

**旁证**（仓库内实测）：
- `game/server/dist/update-source-comments.py` 引用 `src/enums/moves.ts` / `abilities.ts` / `species.ts` —— 与上游 2025 中期目录结构一致
- 无 `.map` 文件、无 `sourceMappingURL` —— 产物被刻意剥离 sourcemap（**说明是 release 构建**，非 dev）

### 进一步精确（C-1 的可执行方案）

```bash
# 用语言目录清单做二分定位（只读操作，零风险）
# 目标：找到同时满足「有 zh-CN/zh-TW」+「无 tl」+「无 es-419」的最后一个 pokerogue-locales commit
git clone --filter=blob:none https://github.com/pagefaultgames/pokerogue-locales
cd pokerogue-locales
git log --oneline --diff-filter=R -- '*zh-CN*' | tail -5    # 找出改名 commit
```

**产物 hash 对齐（更强判定）**：
- 产物 `index-D3KKGO7Y.js` 的 hash 后缀由 Vite 内容哈希生成
- 若能复现构建且 hash 一致 → **版本对齐 100% 确认**
- 若 hash 不一致 → 记录差异（可能是魔改导致的内容变化，属预期）

**结论**：C-1 从「不可验证」升级为「**已被强特征锁定 + 有可执行精确定位方案**」。

## 1.3 构建管线复现（原 C-2）—— ✅ 可行，成本低于预期

### 上游构建要求（联网核验）

| 项 | 实测/核验结论 |
|---|---|
| 包管理器 | **pnpm**（上游 2025-06-24 由 npm 迁移至 pnpm，commit `#6018`） |
| Node 版本 | **22**（`.nvmrc` 于 2025-04-15 更新为 node 22，commit `#5586`） |
| 构建工具 | Vite |
| 源码结构 | `src/` + `public/` + `scripts/` + `test/` |
| locales | **外置 git submodule**（2024-10-02 commit `#4529`，`.gitmodules`） |

**这是关键发现**：

> **locales 是独立 submodule 仓库** (`pagefaultgames/pokerogue-locales`)。这解释了两件事：
> ① 为什么本仓库的 `dist/locales/` 是完好的 JSON（构建时从 submodule 拷入，未参与压缩）
> ② 为什么「上游版本对齐」可以用 locales 命名强特征来锁定

### 构建可行性判定

| 项 | 判定 | 说明 |
|---|---|---|
| 能否复现构建 | ✅ 能 | 上游是标准 Vite + pnpm 项目，公开可构建 |
| 前置成本 | 🟡 中（低于计划书预估的"高"） | 主要是：装 pnpm、装 Node 22、拉 submodule、装依赖 |
| 风险点 | ⚠️ 依赖锁定 | 上游用 `pnpm-lock.yaml`；若目标版本锁文件不可得，依赖版本会漂移 → 需固定 |
| 产物 hash 一致性 | 🟡 预期**不一致** | 魔改改动了源码，hash 必然变。**这是预期的，不是失败** |

**重要认知修正**：

> 计划书把「产物 hash 与现发行版对齐」列为判据（S8 验收 ②）。但这是**错误判据**——因为本仓库是**魔改版**，源码必然与原版不同，hash 必然不同。**正确判据应是**：用**未魔改的上游 baseline** 构建，验证 hash 是否与上游官方发行版一致（验证管线正确性）；然后再叠加魔改。
>
> **两段式验证**：
> ```
> 阶段 1：上游 baseline 构建 → hash 对齐上游官方 release  ✅ 验证管线
> 阶段 2：叠加魔改 → hash 变化  ✅ 预期行为
> ```

## 1.4 资产管线复现（原 C-3）

**实测**（`game/server/dist/`）：

| 资产类别 | 位置 | 是否入库 |
|---|---|---|
| 图片 | `images/`（含 `mingzuo/` 魔改新增目录） | ❌ 二进制不入库 |
| 音频 | `audio/` | ❌ 不入库 |
| 字体 | `fonts/` | ❌ 不入库 |
| 战斗动画 | `battle-anims/` | ❌ 不入库 |
| 本地化 | `locales/`（17 语言 × ~64 文件） | ✅ 文本入库（42 MB） |

**AGPL 视角的重要区分**：

| 资产 | 是否属「Corresponding Source」 | 说明 |
|---|---|---|
| `src/**`（TS 源码） | ✅ **必须提供** | 生成产物的必要源码 |
| `public/**` 下的图片音频 | ⚠️ **视情况** | 属"generate/install/run"所需 → 大概率需提供 |
| `locales/**` | ✅ 必须 | 构建输入 |
| Pokémon 素材本身 | ❌ **不属 AGPL 范围** | 版权归 Nintendo/Creatures/GAME FREAK（`NOTICE.md` 已声明） |

> **法律要点**：AGPL 的源码义务**只覆盖代码**，不覆盖 Pokémon 素材的著作权。但**游戏运行仍需素材** → 所以资产管线必须能复现，否则"可构建"是空话。

**结论**：C-3 的产出应是一份「**资产获取清单**」——哪些可从上游 submodule 获得、哪些有独立许可、哪些需自备。**此项不做代码改动，可立即执行。**

## 1.6 源码化的分步路径（建议）

```
阶段 0（现在，零风险，只读）
  └─ 用 locales 命名强特征锁定上游版本区间（2025-06~08, v1.11.x）
  └─ 产出资产获取清单
  └─ 开始累积「魔改点 → 上游文件」映射表（随 S2–S6 顺手记录）

阶段 1（S7 之后，独立分支）
  └─ clone 上游到锁定版本，装 pnpm + Node 22，复现 baseline 构建
  └─ 验证 baseline 产物 hash 与上游官方 release 一致 → 管线正确性确认
  └─ 【不合并任何魔改】仅验证管线

阶段 2（评估后决策）
  └─ 把魔改点按「新增模块 / 修改现有」两类迁移
  └─ 新增模块（天赋/命座/解明/二游/PT）→ 直接搬，冲突最小
  └─ 修改现有（P5X战斗/游戏模式/UI改动）→ 逐个 rebase，冲突最大

阶段 3（切换）
  └─ 产物从"补丁产物"切换为"源码构建产物"
  └─ 此时 pkrc/ 外置层可逐步内联回源码（或在源码层实现同等能力）
  └─ 补丁通道退役（patch-game.py 归档）
```

**关键洞察：`pkrc/` 外置层是源码化的「过渡桥」**

本次改造（B 路径）产出的 `pkrc/**` 是**有源码的**。这意味着：
- 短期：它在补丁产物上运行
- 长期：**它的逻辑可以逐模块搬进上游源码**，成为源码化的一部分，而不是废弃

> **所以 S0 的「冻结接口设计」有额外的战略价值**：接口设计得好，将来搬进源码时改动最小。**这也是为什么本文档强调 `runtime-bridge.js` 必须接口干净。**

## 1.7 源码化的风险与代价（诚实版）

| 风险 | 等级 | 说明 |
|---|---|---|
| 上游 UI 频繁变更 → 持续冲突 | 🔴 高 | 魔改集中在 `src/ui/**`，是上游改动最活跃区 |
| 依赖版本漂移 | 🟡 中 | 无 lockfile 时构建不可复现 |
| 825 MB 资产不可复现 | 🟡 中 | 二进制不入库，需独立管线 |
| 汉化质量 | 🟡 中 | 社区汉化 vs 上游官方 zh-Hans，需选择 |
| 工作量 | 🔴 高 | C-4 清点显示魔改点遍布 UI 层 |
| **失去补丁的"轻量"优势** | 🟢 低 | 但换来可维护性，值得 |

**诚实的结论**：

> 源码化**技术上完全可行**，上游版本**可以锁定**，构建管线**可以复现**。
> 但它的**真实成本在 C-4（魔改点迁移）**，不在 C-1/C-2/C-3。
> 计划书说「前置条件短期不可验证」——**这个判断偏保守**：C-1/C-2/C-3 现在就可验证（阶段 0 只读、阶段 1 独立分支）。
> **真正的阻塞是：没人做 C-4。**

## D1　Node 运行时策略 🔴

**现状**：便携 `node.exe`（`..\shared\runtime\node.exe`）；`game/package.json` 声明 `express ^4.19.2` + `http-proxy-middleware ^3.0.0`。

**必须现在决定的点**：

| 问题 | 影响 |
|---|---|
| 便携 Node 的**具体版本号**？ | 决定可用语法（`?.`/`??`/顶层 await）与 Express 5 兼容性 |
| 是否允许依赖系统 Node？ | 便携 = 免安装但体积大；系统 = 轻但需用户预装 |
| Node 版本与 Electron 内嵌的 Node 是否冲突？ | S7 合并进程时，Electron 自带 Node，**便携 Node 可能变多余** |

**推荐**：
- ✅ **保留便携 Node**（免安装是卖点）
- ✅ **记录确切版本号**（写入 `docs/tech-stack-decision.md`）
- ⚠️ **S7 时重新评估**：Electron 内嵌 Express 后，便携 Node 只剩 `--serve-only` 场景需要

## D2　Electron 壳策略 🔴

**现状**：Electron **25.7.0** + Nativefier 52.0.0，窗口 1280×800；`pokerogue-win32-x64` 时间戳 **2024-05**。

**核心决策：要不要升级 Chromium？**

| 选项 | 收益 | 风险 | 推荐 |
|---|---|---|---|
| **不升级**（保持 25.7.0 / Chromium 114） | 零风险；已验证可用 | 新 CSS/JS 特性支持受限 | ✅ **本次推荐** |
| 升级到最新 Electron | 新特性支持 | 需重测全部渲染、缩放、DPI；炸了要回滚 | ❌ 本次不做 |

**理由**：计划书根因 D 指出「版本错配是不确定性来源」。但**升级本身引入更大的不确定性**——本次改造的视觉层（S5）依赖稳定的渲染行为，换 Chromium 会让「改造前 vs 后」的对比失去基准。

> **正确顺序**：先完成本次改造（在稳定的 Chromium 114 上建立视觉基准）→ 再单独评估 Chromium 升级（独立分支、独立回归）。

**另一决策点：Nativefier vs 自写主进程** —— 计划书已推荐自写（S7），**本文档确认同意**，理由：Nativefier 无法接管焦点/缩放/DPI/多显示器事件，而这正是输入层与视觉层需要的。

## D3　依赖策略 🔴

**实测**（`game/package.json`）：

```json
{
  "dependencies": {
    "express": "^4.19.2",
    "http-proxy-middleware": "^3.0.0"
  }
}
```

**关键决策：本次改造能否新增运行时依赖？**

| 选项 | 风险 |
|---|---|
| ✅ **禁止新增** | 便携离线环境下，新增依赖需保证能被正确打包；`^` 语义化版本在无 lockfile 时会漂移 |
| ❌ 允许新增 | 部署风险；离线环境下缺依赖 = 直接起不来 |

**推荐：禁止新增运行时依赖。**

**`^` 版本符的隐患**（实测发现）：

> `"express": "^4.19.2"` 意味着**任何 4.x 版本**都可被安装。若便携包内的 `node_modules` 与 `package.json` 不同步，行为可能不一致。
>
> **行动**：核对便携包内实际安装的 Express 版本，并考虑**锁定为精确版本**（去掉 `^`）。

`http-proxy-middleware` 的用途需确认（可能是开发期代理，生产可移除）。

## D4　配置文件格式 🔴

**计划书的示例用 `jsonc`（带注释）**，但产物运行时用的是标准 `JSON.parse`。

| 格式 | 可解析性 | 推荐 |
|---|---|---|
| `jsonc`（带注释） | ❌ 需额外解析器 | 不推荐 |
| **标准 JSON** | ✅ 原生 `JSON.parse` | ✅ **推荐** |
| YAML | ❌ 需新依赖（违反 D3） | 不推荐 |

**已在 `docs/delegation/` 三份派单中纠正**：所有配置文件（`input-config.json` / `theme-config.json` / `runtime-config.json`）必须是**无注释的合法 JSON**。

> **注意**：若将来需要配置文件注释能力，正确做法是**新增 `.md` 说明文档**（或者引入 JSONC 解析器，但违反 D3）。

## D5　存档格式兼容策略 🟠

**现状**：`.prsv` 加密存档，落在 localStorage / IndexedDB；`tools/save-editor` 可解析。

**核心风险**（计划书 R6）：**换 Electron 壳会改变 `userData` 目录 → 存档可能丢失**。

**必须现在冻结的决策**：

| 决策 | 内容 |
|---|---|
| **存档格式冻结** | 本次所有改造（S0–S8）**不得触碰**存档序列化与加密 |
| **换壳前置** | S7 前必须：导出全量存档 → 换壳 → 验证导入成功（计划书已列，本文档强化） |
| **存档路径** | 明确记录 localStorage / IndexedDB 绑定的具体 `userData` 子路径 |
| **降级方案** | 若换壳导致存档丢失 → 保留 Nativefier 壳作为回退目录（计划书已列） |

**另需决策**：手否提供**跨壳存档迁移工具**？（把旧 `userData` 的存档导入新 `userData`）
- **推荐**：提供。这是 S7 的**安全网**，成本不高（本质是文件拷贝 + 路径映射）。

## D6　i18n 架构 🟠

**实测**：**1808 条中文字符串字面量**内联在 `loading-scene-*.js`；仅 `talentViewer`/`talentCodex` 走了 i18n。

**决策点**：

| 选项 | 说明 | 推荐 |
|---|---|---|
| 内联（现状） | 无法切换语言、无法统一改词 | ❌ |
| **外置命名空间** | `pkrc<系统>.<模块>.<键>` | ✅ **推荐** |
| 复用上游 i18n 命名空间 | 与上游 key 冲突风险 | ❌ |

**关键洞察**：

> 上游的 locales 是**外置 submodule**（实测 `.gitmodules`）。这意味着**上游官方 zh-Hans 汉化是持续维护的**。
>
> **决策影响**：源码化后，`pkrc.*` 命名空间与上游命名空间**可以共存**。魔改新增系统的文案走 `pkrc.*`，原版系统的文案走上游 key —— **互不干扰**。这是源码化的一个额外收益。

**已在前序派单中落实**（`docs/delegation/04-UI设计师-派单.md` §3.2）。

## D7　测试策略 🟠

**现状**：无源码 → 无法用上游的 Jest 测试；现状只有手工回归。

**核心矛盾**：**外置层有源码，产物无源码。**

**推荐：双轨测试**

| 轨道 | 对象 | 方法 |
|---|---|---|
| **轨 1：单元测试** | `pkrc/**` 纯逻辑（`gesture-resolver` / `input-arbiter`） | Node 内单测（已在前端派单中要求「导出纯函数」） |

| **轨 3：手工回归** | 产物行为 | 计划书 §2.10 的回归清单 |
| **轨 4：视觉回归** | 视觉层 | 截图对比（UI 派单已列） |

**关键要求**（需写入决策文档）：

> **`pkrc/**` 中所有纯逻辑模块必须能在 Node 中运行单测**——这是本次改造能获得"可测试性"的唯一机会。若把逻辑写死在 Phaser 依赖里，就永久失去了单测能力。

**已在前端派单中落实**（要求 `gesture-resolver.js` 导出纯函数、可在 Node 单测）。
