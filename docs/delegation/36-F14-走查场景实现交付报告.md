## 三、核心设计：为什么必须做「五态裁定」

派单 P5-R3 要求区分「某系统走查不过」与「该系统迁移不完整」，P5-R5 要求「按系统分批交付」。
而 F-12 的 catalog 原本只有 `verified/designed` 两态，跑起来只能报 pass/fail —— **这两件事会被混成一个数字**。

### 3.1 五态定义

| 裁定 | 含义 | 进哪本账 | 算走查失败 |
|---|---|---|---|
| `pass` | 到达有**强证据** + 断言全过 | — | 否 |
| `fail` | 到达了但断言不过 / 新增未捕获异常 | 缺陷台账 | **是** |
| `unproven` | route 跑完、断言过，但**到达证明不足** | A4-01 待办 | 否（**但不得声称已走查**） |
| `unreached` | route **明确失败**（画面没变 / 步骤报错） | A4-01 待办 | 否 |
| `blocked` | **该产物里没有这个画面的代码**（gate 未命中） | L2/L3 迁移台账 | 否 |

### 3.2 `unproven` 是这套设计的关键（也是最容易造假的地方）

Phaser canvas 内的文本**不在 DOM**（U-11 已记），页面读不到「当前是哪个界面」；
游戏又不暴露模块作用域内的全局对象。所以「按了几下键 + 画面变了」**不等于**「到了那个界面」。

若把弱证明记成 `pass`，就是拿弱证明冒充「已走查」—— 这正是 O-8「可编译 ≠ 功能等价」的同类错误。
因此新增 `reachProof` 字段，把到达证明分级：

| `reachProof` | 含义 | 计入 `pass`？ |
|---|---|---|
| `inject` | 注入了**真存档**（键名匹配 `data_*` / `sessionData` / `mappingConfigs` / `settings`） | ✅ |
| `dom` | 页面可读断言命中（仅 HTML 模块） | ✅ |
| `none-verified` | 无导航但已实测可达（`boot.ready`） | ✅ |
| `weak` | 只有「画面变了」 | ❌ → `unproven` |
| `none` | 无任何证明 | ❌ → `unproven` |

⚠️ **防呆**：`--inject '{"__wt_probe__":"ok"}'` 这类**哨兵注入不算到达**（它只验证注入通道，游戏仍停在标题页）。
实测已守住这条：同一命令下 `healer.wish` 由「假 pass」正确回落为 `unproven`。

## 四、核心设计：产物闸门（为什么走查前必须先查「有没有实现」）

### 4.1 问题

`mod-init.ts` 末尾自己写着挂账：

```
// ⚠️ A4-00 遗留（挂账）—— 以下系统的初始化入口**尚未接上**（缺 mod 侧注册函数）：
//   · nianli / p5x / ERYOU ×2（4 个 Phase + **11 个 UI Handler 挂到 UI 模式注册表**）
```

而 `src/ui/ui.ts` 的 `this.handlers` 只从 `#data/systems/mod-squad-hud` 引了 `updateSquadBattleHud`，
**没有任何 mod UiHandler 被实例化** ⇒ 这些界面在 B（自构建）里被 tree-shake 摇掉，
永远不会渲染。若不前置判定，走查会把「没实现」和「实现错了」记成同一个 fail。

### 4.2 🔴 方法学发现：**B 产物未启用 keepNames**

| 标识符 | A（modder） | B（自构建） |
|---|---:|---:|
| `MenuUiHandler` | 1 | **0** |
| `TitleUiHandler` | 1 | **0** |
| `BattleMessageUiHandler` | 1 | **0** |
| `StarterSelectUiHandler` | 1 | **0** |
| `SettingsUiHandler` | 3 | **0** |
| `ChallengesUiHandler` | 1 | **0** |

⇒ **任何「按标识符名 grep 产物」的探测在 B 上恒为假。**
gate 必须只用**字符串字面量**（中文文案 / i18n key / 资源 key），这些压缩后仍完整保留。

## 五、route 可靠性（如实）

| 级别 | 点数 | 含义 |
|---|---:|---|
| `verified` | **2** | 本环境已实测（`boot.ready`、`boot.welcome-popup`） |
| `derived` | **22** | 依代码证据推导（菜单项 / UiMode / 挑战列表 / 战斗内 HUD） |
| `unknown` | **27** | 暂无可推导的到达依据（ERYOU 界面、命座、超背包、多数战斗内触发点） |

`derived`＋`unknown` 合计 49 点，与 F-12 §五「verified 2 / designed 49」**完全一致** —— 没有虚增。

**route 为何不能更多 `verified`**：
不是偷懒，而是**当前缺乏强 oracle**。canvas 读不到文本、游戏不暴露全局对象，
`derived` 的菜单索引（`M` → 下移 N 次 → 确认）必须在真机逐条实测才能升级为 `verified`，
而这正是 **A4-01 的工作内容**（F-12 §五已明示「不该在清单阶段假装完成」）。
F-14 把这件事变成**可执行 + 可裁定 + 有清单**，而不是停在文字描述。
