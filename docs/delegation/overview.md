## 做了什么

把 PKRC 改造实施计划按**职责边界**拆成四份可独立执行的派单文档 + 一份共用协作契约 + 一份任务看板。每份派单都是自包含的：含问题根因、具体任务、数据结构契约、验收判据、交付清单、关键假设。

## 关键分工决策

**1. 谁先动：全栈拿 S0**
运行时钩子补丁 + 装配入口是**所有人的前置**（前端与 UI 阻塞于此）。全栈是唯一关键路径起点。

**2. 谁最重：前端拿 S2/S3/S4**
输入层重构占全项目约 50% 工作量。核心目标是把「散落的 pointerdown + 强制常驻的移动端虚拟手柄」重构为统一、可配置、可禁用的交互层。

**3. 谁最能独立开工：后端**
后端拿下 S1 服务层 + S8。这是全项目唯一**不阻塞任何人**的模块，可立即开工；S8 源码化评估同时是战略价值最高项。

**4. 唯一易混淆处的边界切割**
| 冲突点 | 切割规则 |
|---|---|
| S1「启动」阶段 | **全栈管外壳**（VBS/bat/Electron 主进程）；**后端管服务层**（server.cjs/日志/端口策略） |
| `#touchControls` 虚拟手柄 | **UI 管 CSS**（移除 3 条 `!important` + 兜底隐藏规则）；**前端管行为开关**（`virtualPad.mode`，JS 控制 class） |

**5. UI 可提前开工**
Token 体系设计 + 27 种野生字号的映射表是**纯设计工作**，不依赖运行时 —— 已明确从 S5 中拆出，让 UI 不必干等 S0。

## 发现并修正的计划书隐患

| 隐患 | 说明 | 处置 |
|---|---|---|
| `jsonc` 注释 | 计划书配置文件示例标为 `jsonc`（含注释），但产物实际必须是**合法 JSON**（无注释），否则 `JSON.parse` 直接失败 | 已在后端/前端/UI 三份派单中显式标注纠正 |
| S1 职责未切分 | 计划书未说明启动阶段由谁主责，存在全栈与后端撞车风险 | 已补充切割规则（见上表） |
| 字号收敛缺映射依据 | 计划书只给了 7 级目标值，未给出 27 种野生值如何吸附 | 已补充「最近邻映射表」+ 偏差审查要求（含 `micro=36` 的选值理由） |
