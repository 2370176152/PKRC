## 一、甄别结论：B0 与上游存量的实测重叠率

### 1.1 方法

对 24 个去重文案做 **value 反查**，索引覆盖两处存量：

| 存量 | 路径 | keys 数 |
|---|---|---|
| 上游源码（M5 后的源） | 锚点树 `locales/zh-Hans/**`（64 文件） | 6,371 |
| 改版当前产物 | `game/server/dist/locales/zh-CN/**`（64 文件） | 5,316 |

### 1.2 结果：命中 1 / 24

| 文案 | 上游命中 | 改版产物命中 | 处置 |
|---|---|---|---|
| **返回** | `menu:goBack` ／ `settings:back` | `settings:back` | ✅ **复用 `menu:goBack`**（导航语境，settings 页变体不取） |
| 其余 23 个 | ❌ 无 | ❌ 无 | 全部新建 `pkrc.common.*` key |

> ⚠️ **对 U-2 批次卡的实证修正**：批次卡称 B0「与上游 `common.json` 大量重叠（上游已有 8,679 条中文值）」。
> 实测：① 上游 zh-Hans 全量 **6,371 keys**（非 8,679，口径存疑）；② B0 的 29 条与上游**实际重叠仅 1 条**。
> 根因：批次卡的「典型文案」列（稀有/史诗/金币/背包…）是**按命名空间语义设想的示例**，不是 manifest 实际收录内容。
> **教训**：B6a（P5X）也有同款预警（「与 battle.json 可能重叠」），届时同样以实测为准。

### 1.3 为什么重叠率低——manifest 的分类规则（新发现）

逐行核对产物后确认，U-2 扫描器的规则是**行级单系统继承**：

1. 每行按**系统标识符**判定归属（命中 `talent:` 等前缀 → TALENT；无标识 → 兜底）；
2. **短文案（无标识行）→ COMMON**，**长文案（无标识行）→ LEGACY**（B6b 待甄别）；
3. 行内所有中文串**继承该行**的系统归属。

证据：L335 一行 10 条记录，5 个天赋名（快板/和声/渐强/终曲/回响）→ COMMON，5 条 description → LEGACY。

**推论**：B0 的实际成分 = 「分布在无标识行上的短文案」= **天赋名 + 系统术语**，与 `pkrc.common`（通用提示）的命名空间语义**不匹配**。

## 三、`pkrc-common.json`（24 keys）与命名空间注册

### 3.1 条目数对账（为什么是 24 而不是 23/25）

```
manifest COMMON 记录        29 条
  ↓ 按文本去重
去重文案                    24 个（回响出现 2 次但语义不同）
  ↓ 「返回」复用上游，不新建
需新建 key 的文案           23 个
  ↓ 「回响」拆 2 个 key（melodyEcho / shockEcho）
pkrc-common.json  keys      24 个 ✅
```

**「回响」拆 key 的理由**：L335 是音律天赋（`[节拍]上限由 X 提升到 Y`），L351 是感电天赋（`单体招式命中后随机再释放一次`）——**两个不同天赋共用显示名**。若合并为一个 key，将来任一天赋改名会误伤另一个；且 B1（TALENT）迁移时两者本就要分赴 `talent:talents.<id>.name`。现在拆开，映射表可无歧义追溯到具体产物行。

### 3.2 命名规则

- **前缀编码系统语境**（甄别时人工判定，防丢信息）：`melody*`（音律）/ `shock*`（感电）/ `mend*`（治疗）/ `psy*`（念力）/ `ember*`（火系）/ 无前缀（真通用）。
- camelCase，与上游既有 key 风格一致（`goBack` / `ptBalance`）。
- 该前缀同时服务 **B1 重分类**（见 §五.2）：迁移到 `pkrc.talent` 时按前缀批量归队。

### 3.3 注册配方（S7-4 施工必读，三个触点）

| # | 触点 | 动作 | 是否必须 |
|---|---|---|---|
| 1 | 文件落地 | `locales/<lng>/pkrc-common.json` | ✅ |
| 2 | `src/i18n-namespace-map.ts` | 加 `"pkrc.common": "pkrc-common"` | ✅ **必须**——`toKebabCase()` 不拆点号（`DELIM_STRIP_REGEXP = /[-_ ]+/`），`pkrc.common` 会解析成 `pkrc.common.json` 而非 `pkrc-common.json` |
| 3 | `ns: nsEn` 清单 | **无需手工登记** | — `nsEn` 由 `namespaces-i18n-plugin.ts` 构建时爬 locales 目录自动生成，且会按 namespaceMap 反查换名 |

**调用形式**（i18next 默认 `nsSeparator=":"`，上游无覆盖配置）：

```ts
M.t("pkrc.common:melodyAllegro")   // ✅ 正确
M.t("pkrc.common.melodyAllegro")   // ❌ 会被当作 defaultNS 的嵌套 key，取不到值
```

> ⚠️ U-2/U-3 文档中 `t("pkrc.common.xxx")` 的点号写法是**简写记号**，实际代码必须用冒号。已在本派单周期内统一口径。

### 3.4 语言目录风险（移交 M5 交接）

上游锚点树语言代码是 **`zh-Hans`**（`supportedLngs` 白名单内），改版当前产物用的是 **`zh-CN`**（dist 目录名）——两者不一致。B0 文件落地时须确认 M5 后的语言目录名，否则 `loadPath` 指向空目录。**已列入 A5-03 底座交接 checklist 建议项**。

## 五、待决问题与建议（需前端/全栈会签）

### 5.1 「回响」拆 key 已按推荐方案执行（melodyEcho / shockEcho）

如前端倾向合并为单 key，需同时接受「两个天赋显示名永久绑定」的后果——**不建议**。

### 5.2 建议：B0 的 18 个天赋名 key 在 B1 执行时重分类至 `pkrc.talent`

24 个去重文案中 **18 个是天赋名**（音律 5 + 感电 4 + 治疗 5 + 念力 2 + 火系 2）。它们与 B1（TALENT 1,659 条）的 `talent:talents.<id>.name` 模式同构，继续放在 `pkrc.common` 会造成「天赋名散居两处」。

**建议**：B1 施工时把这 18 个 key 迁到 `talent:talents.<talentId>.name`（talentId 由 A3-06 迁移时确定），`pkrc-common.json` 仅保留 6 个真通用项（currentPokemon / tagFallback / breakthrough / breakthroughMaxed / backToLobby / controlResist）。**本条不阻塞 U-5 验收**，作为 B1 的输入建议。

### 5.3 namespaceMap 条目需写入 S7-1 施工单

`"pkrc.common": "pkrc-common"` 是 B0–B6 全部批次的前置（B2–B6a 同样需要 `pkrc.mingzuo` → `pkrc-mingzuo` 等 6 条同类条目）。建议在 U-6 适配层文档中汇总成一张 namespaceMap 增量表，一次加齐。
