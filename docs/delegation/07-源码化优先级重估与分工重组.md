# 源码化优先级重估 + 任务分工重组方案

> **触发**：用户确认「**不对外分发**」
> **结论先行**：源码化的优先级从 **「紧急合规项」降为「纯工程优化项」**；**四人分工框架不变**，但**任务权重、依赖顺序、里程碑需要重组**——且有一个**新增的关键角色空缺**需要填补。
> **编制日期**：2026-10-13

# 第一部分　「不对外分发」的法律后果重估

## 1.1 AGPL-3.0 义务的精确触发条件（逐条对照原文）

AGPL 的义务**不是"用了 AGPL 代码就有义务"**，而是**由特定行为触发**。逐条核对 `LICENSE` 原文：

### 条款 A：第 1 条「Corresponding Source」（LICENSE 第 122–141 行）

> The "Corresponding Source" for a work in object code form means all the source code needed to generate, install, and run the object code...

**触发条件**：**分发（convey）目标代码**（object code）。

### 条款 B：第 13 条「Remote Network Interaction」（LICENSE 第 540–551 行）

> **if you modify the Program**, your modified version must prominently offer all users **interacting with it remotely through a computer network** (if your version supports such interaction) an opportunity to receive the Corresponding Source...

**触发条件**：① 修改了程序 **且** ② 让用户**通过网络远程交互**（SaaS 场景）。

### 条款 C：「propagate」与「convey」的法定定义（LICENSE 第 80–89 行）

> To **"propagate"** a work means to do anything with it that, without permission, would make you directly or secondarily liable for infringement under applicable copyright law, **except executing it on a computer or modifying a private copy**.
>
> To **"convey"** a work means any kind of propagation that **enables other parties to make or receive copies**. **Mere interaction with a user through a computer network, with no transfer of a copy, is not conveying.**

## 1.2 三种场景的义务判定

| 场景 | convey? | propagate? | 第 1 条义务 | 第 13 条义务 |
|---|---|---|---|---|
| **A. 只自己在本机玩（不传出任何副本）** | ❌ 否 | ❌ 否（「except executing it on a computer」） | **无** | **无** |
| **B. 内部小范围共享（发给朋友 / 团队内部）** | ✅ **是**（"enables other parties to make or receive copies"） | ✅ 是 | ✅ **必须提供 Corresponding Source** | ❌ 否（非网络远程交互） |
| **C. 对外公开发布（网盘 / GitHub / B站分发）** | ✅ 是 | ✅ 是 | ✅ **必须** | 视是否有 SaaS |
| **D. 部署成在线服务（云游戏 / 网页版）** | ⚠️ 视是否传副本 | ✅ 是 | 视情况 | ✅ **必须**（第 13 条正中此场景） |

## 1.3 「不对外分发」的准确含义需要界定

⚠️ **「不对外分发」是一句模糊的话，法律后果取决于它的准确含义。** 必须区分：

| 用户的可能含义 | 判定 | 源码化优先级 |
|---|---|---|
| **α. 完全自用**（只有自己，连朋友都不给） | 场景 A → **零义务** | 🟢 **纯优化，可无限期延后** |
| **β. 只在小圈子内共享**（发给几个朋友 / 群友） | 场景 B → **仍有源码义务** | 🟠 **有义务，但无外部监督压力** |
| **γ. 不公开发布，但成品给了别人用** | 场景 B/C 之间 | 🟠 **同上** |

**关键论断**：

> **「不对外分发」若指 α（完全自用），则 AGPL 义务归零，源码化从"合规必需"彻底降为"工程优化"。**
> **若指 β（小圈子），义务仍在，但因为没有公开发布，实践上不存在被追责的现实风险。**
>
> **但这不改变一个技术事实**：无论哪种情况，**「产物即源码」的工程代价（R8）依然存在**——补丁模式在每次上游更新时都要重做。

**建议**：即使法律义务归零，源码化仍有**独立的工程价值**，只是优先级可以放缓，不必抢占本次改造的资源。

# 第二部分　对四人分工的冲击分析

## 2.1 分工框架：**不变**

四人分工（全栈 / 前端 / 后端 / UI）是按**技术层次**切的，不是按合规切的。合规优先级变化**不改变技术分层**。

**所以答案的第一层是：✅ 不需要重组分工框架。**

## 2.2 但**任务权重**需要重组

源码化优先级降级后，出现两个连锁变化：

### 变化 1：S8 从「后端独担」变为「可拆解」

原分工把整个 S8 压给后端，理由是「战略价值最高」。降级后：

| 原 S8 子任务 | 新归属 | 理由 |
|---|---|---|
| S8-1 决策文档 | 后端 | 不变 |
| S8-2 C-1 版本锁定 | 后端 | 不变（只读，低成本） |
| S8-3 报告补充 | 后端 | 不变 |
| **S8-4 C-2 构建复现** | **⚠️ 转交「新角色」** | 需要 pnpm/Node22/上游源码，是**独立工程**，与现有任何人职责都不吻合 |
| **S8-5 C-4 魔改点迁移** | **⚠️ 转交「新角色」** | 工作量最大，是源码化的真阻塞 |
| S8-6 资产清单 | 后端 | 不变 |

### 变化 2：出现**关键角色空缺** 🔴

**这是本报告最重要的结论。**

源码化（阶段 1–3）的工作性质与现有四角色**都不吻合**：

| 现有角色 | 为什么不吻合源码化 |
|---|---|
| **全栈** | 熟悉「产物 + 补丁 + 外置层」范式；但源码化需要**上游 TS 源码工程经验**（Vite/pnpm/TS 构建/上游代码库导航），技能栈不同 |
| **前端** | 前端在做 S2–S4（输入层重构），已是最重负荷；且其工作对象是**产物**，源码化的工作对象是**上游 TS 仓库** |
| **后端** | 后端负责服务层（Express/日志/进程）；源码化是**构建工程**，不是服务工程 |
| **UI** | UI 在做 S5–S6（视觉/文案）；源码化需要的是**构建与依赖管理**，不是视觉 |

**空缺的本质**：

> **源码化需要的是一个「构建/发布工程师」（Build & Release Engineer）或「上游维护者」（Upstream Maintainer）角色** —— 职责是：维护上游 fork、复现构建管线、合并上游更新、迁移魔改点。
>
> 这是一个**长期存在**的职责（不是一次性任务），因为源码化之后**每次上游更新都需要这个角色**。

## 2.3 两个可选的组织方案

### 方案一：「第 5 角色」专职（推荐用于源码化启动后）

```
新增角色：构建/上游维护工程师（Build & Upstream Engineer）
  ├─ 职责：上游 fork 维护、构建复现、魔改点迁移、上游合并
  ├─ 触发时机：源码化进入「阶段 1」时才真正需要
  └─ 阶段 0（只读评估）仍可由后端代劳
```

**优点**：责任清晰、技能匹配、可持续
**缺点**：需要新增人力

### 方案二：全栈「兼」构建职责（推荐用于源码化延后）

```
全栈工程师扩展职责：
  ├─ 原职责：S0 底座 + S1 启动器 + S7 Electron 主进程
  └─ + 新增：源码化阶段 1–3（构建复现 + 魔改迁移）
```

**优点**：不加人；全栈本来就最懂「产物如何生成」（S0 的钩子补丁就是"产物逆向"技能）
**缺点**：全栈在 S0/S7 期间已满负荷；源码化排在其后（时间上不冲突）
**关键理由**：全栈做 S7（自写 Electron 主进程 + 内嵌 Express）时，已经需要理解上游构建产物结构；**S7 与源码化阶段 1 有技能重叠**。

### 推荐：**方案二为主，方案一为备**

| 时点 | 组织方式 |
|---|---|
| **现在 → 本次改造完成** | 全栈兼管「阶段 0 只读评估」（与 S0 同源技能） |
| **S7 完成后** | 评估是否引入第 5 角色；若全栈已熟悉上游构建，则继续兼 |
| **源码化规模化后** | ✅ **必须独立第 5 角色**（因为上游合并是持续性工作） |

# 第三部分　重组后的分工与顺序

## 3.1 修订后的角色职责表

| 角色 | 原职责 | **修订后** | 变化 |
|---|---|---|---|
| **全栈** | S0 + S1外壳 + S7 | S0 + S1外壳 + S7 + **源码化阶段 0/1（兼）** | 🔼 增责 |
| **前端** | S2/S3/S4 | S2/S3/S4（**不变**） | ⬆️ **相对权重上升**（成为唯一纯本次改造的重负荷角色） |
| **后端** | S1服务层 + S7服务侧 + S8 | S1服务层 + S7服务侧 + **S8 缩减为文档与只读评估** | 🔽 减责 |
| **UI** | S5/S6 | S5/S6 + **随 S6 顺手记录魔改点映射** | ➡️ 不变（+零边际成本项） |
| **（新增）构建工程师** | — | 源码化阶段 1–3 | 🆕 待触发 |

## 3.2 修订后的优先级顺序

**核心变化：源码化从「阻塞性合规项」变为「可延后的优化项」**

```
【本次改造 —— 优先级不变，全部照原计划执行】
S0（全栈）── 关键路径起点，仍然最高优先级
  ↓
S1（全栈外壳 + 后端服务层）── 可并行
S2 → S3 → S4（前端）── 工作量最大
S5 → S6（UI）── 可与前端并行
S7（全栈 + 后端）

【源码化 —— 优先级下调】
阶段 0（只读评估）──── 现在可做，零风险，不影响本次改造
  ├─ 上游版本锁定（后端，低成本）
  ├─ 资产清单（后端，低成本）
  └─ 魔改点映射表（前端+UI 随 S2–S6 顺手累积，零边际成本）

阶段 1（构建复现）──── ⏸️ 延后到 S7 完成之后
阶段 2（魔改迁移）──── ⏸️ 视阶段 1 结果再定
阶段 3（产物切换）──── ⏸️ 长期
```

## 3.3 关键判断：**源码化不该抢占本次改造的资源**

| 论据 | 说明 |
|---|---|
| **合规压力消失** | 不对外分发 → 无追责风险 → 无紧迫性 |
| **技术债仍在但可控** | 补丁模式的技术债（R8）在"自用"场景下，痛感大幅降低（不用追随上游更新） |
| **本次改造本身就在缓解 R8** | `pkrc/**` 外置层是**有源码的** → 已经把"新增代码"从技术债中摘出来 |
| **源码化的真阻塞是 C-4** | C-4 依赖本次改造的产出（魔改点清点）→ **先做本次改造，才能做源码化** |

> **最重要的顺序洞察**：
> **本次改造（B 路径）是源码化（C 路径）的前置，而不是替代品或竞品。**
> S2–S6 在做输入层与视觉层时，会**天然摸清每一个魔改点**——这正是 C-4 的输入。
> **所以：先把 B 做完、做扎实，C 的成本自然降下来。**

# 第四部分　需要补强的两处（因优先级变化而产生）

## 4.1 补强 1：`pkrc/**` 的「可迁移性」要求升级 🔼

**原因**：源码化降级后，`pkrc/**` 从「过渡桥」变成**更长期的载体**——它可能长期与补丁产物共存。同时它也是未来迁移进源码的素材。

**要求升级**（需写入派单 01/02/04）：

| 原要求 | 升级后要求 |
|---|---|
| 外置层可单文件禁用 | + **每个模块必须可独立迁移**（不依赖外置层的私有约定） |
| 接口冻结（`runtime-bridge`） | + **接口语义与上游概念对齐**（如 `scene.ui.mode` 而非自造名词） |
| 用 Phaser API 操作场景 | + **避免使用产物内私有方法**（如 `this.onXxxPointer`）；只用上游公开 API 等价物 |

**理由**：若 `pkrc/**` 依赖产物的压缩变量名或私有方法，迁进源码时仍需重写；若只用上游公开 API，则迁移成本接近零。

**这条要求的实施成本很低**（本来就要写代码），但**收益是长期复利的**。

## 4.2 补强 2：S6 的文案抽取任务升级 🔼

**原因**：i18n 化（1808 条文案）原本只是"视觉规范性"任务。现在多了一层价值：

> **文案抽取 = 魔改点的部分清点**（哪些系统是魔改新增的，文案里一目了然）

**要求**（需写入派单 04）：
- 在抽取文案时，**同步标注每条文案所属的魔改系统**（天赋/命座/解明/二游/PT/原版）
- 产出**「魔改系统 → 文案文件 → 上游是否有对应」**的三列映射

**这条**直接喂给 C-4（魔改点迁移清点），**零边际成本**。

# 第五部分　给决策者的三个选项

## 5.1 选项对比

| 选项 | 内容 | 成本 | 适用 |
|---|---|---|---|
| **α. 冻结源码化** | 本次改造完成前不做任何源码化动作（含阶段 0） | 最低 | 若「完全自用」且**永不打算更新版本** |
| **β. 只做阶段 0**（推荐） | 只读评估 + 顺手记录魔改点映射，**不碰构建** | 极低（近似零） | ✅ **推荐**：保留未来可能性，成本几乎为零 |
| **γ. 全速推进** | 阶段 0+1 同步启动，与本次改造并行 | 高（需要第 5 角色） | 仅当确有源码化需求（如计划持续更新版本） |

## 5.2 推荐：**β（只做阶段 0）**

**理由三条**：

1. **成本近似为零**：阶段 0 全是只读操作 + 本次改造顺手记录，不占额外资源
2. **保留选项权**：将来若改变主意（如决定对外发布、或想追随上游更新），已有版本锁定 + 魔改点清单在手，启动成本极低
3. **不干扰本次改造**：S0–S7 的优先级、分工、里程碑**完全不变**

**唯一需要你决策的**：是否愿意让前端与 UI 在 S2–S6 中**顺手记录魔改点映射**（约增加 5% 工作量）？
- 若愿意 → **β 方案成立**，收益是未来源码化的启动成本大幅降低
- 若不愿意 → **α 方案**，但将来启动源码化时需从零做 C-4 清点
