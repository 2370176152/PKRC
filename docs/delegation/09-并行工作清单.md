## 1.3 BLOCK-3：clone 卡住 —— ❌ **原判断有误，已实测纠正**

> **🟢 2026-10-13 第一阶段实测（后端）**：**直连 GitHub 完全可用**，clone 卡住的**根因不是代理**。
> 详见 `docs/tech-stack-decision.md` §0（M-1）与 §3.1（D10）。

**实测证据**：

```bash
# 直连（不用 ghproxy），depth=1 单分支 → 21 MB，数十秒完成
git clone --depth 1 --single-branch --branch beta \
  https://github.com/pagefaultgames/pokerogue.git
# → 退出码 0；src/ 完整（含 src/ui/handlers/ 全部 handler）
```

| 项 | 原文档判断 | 实测 |
|---|---|---|
| 直连可用性 | 「换代理源，或直连」（作为后备） | ✅ **直连本就可用**，无需代理 |
| 根因 | 「代理不可用/限速」或「promisor 被代理阻断」 | ✅ **promisor（`--filter=blob:none`）的按需拉取**在受限网络下反复超时 |
| 建议方案 | 「放弃 partial clone，改完整 clone（稳但慢）」 | ✅ **更好**：`--depth 1 --single-branch`，又快又稳（21 MB） |
| `ghproxy.net` | 保留 | ❌ **可以去掉** |

**为什么 `blob:none` 反而更脆弱**：promisor 模式下，工作区每个文件都要**二次请求 remote** 去补 blob。网络一旦抖动，这些零星请求超时 → 表面现象就是「卡住」——而实际上主仓库握手是成功的。

**正确命令（可直接执行）**：

```bash
# 1. 浅克隆上游（快，但有代价：丢历史）
git clone --depth 1 --single-branch --branch <LOCKED_REF> \
  https://github.com/pagefaultgames/pokerogue.git upstream-pokerogue

# 2. 拉两个资源 submodule（文件名已实测确认）
cd upstream-pokerogue
git submodule update --init --depth 1 assets locales

# 3. 版本定位【不要】靠主仓库历史 → 走 locales 独立仓库（可全量克隆）
git clone --filter=blob:none --no-checkout \
  https://github.com/pagefaultgames/pokerogue-locales
```

**⚠️ 重要权衡（修正版）**：

> `--depth 1` 快，但**丢历史** → **无法靠主仓库历史定位版本**。
> 所以 **A0-2 的版本定位必须走 `pokerogue-locales` 独立仓库**（体积小、可全量克隆、有完整历史），
> 用中文目录 `zh-CN` → `zh-Hans` 的改名 commit 作硬特征。
> **该步已完成** → 硬上界 **2025-09-22**，见 `tech-stack-decision.md` §2.1。

**旧方案留档（已不推荐）**：

| 旧对策 | 现在怎么看 |
|---|---|
| 换代理源 | 不需要——直连可用 |
| 改「完整 clone」 | 可行但慢；`--depth 1 --single-branch` 更优 |
| 用 `PKRC-repo.bundle` 离线 bundle | 那是**本仓库**的 bundle（`git bundle list-heads` → `refs/heads/master` = `4b6fe00`），**不含上游**，解决不了这个问题 |

**测试中发现并修掉的真实缺陷（记录在案）**：

| # | 缺陷 | 影响 | 修法 |
|---|---|---|---|
| 1 | `flatten` 被用在 `stringify` **之前** | 多行 stack 漏网 → 一条日志占多行，破坏格式契约 | 改为一律 `flatten(stringify(x))` |
